# 审批策略设计：为什么"要不要人工审批"不是一个布尔

> 本文说明这套 harness 如何决定**一次工具调用该不该停下来等人**。
> 结论：它是一个三档决策（自动放行 / 问人 / 直接拒），由工具的风险策略与**兜底机制是否到位**
> 共同决定 —— 而不是一个绑在工具上的 `requires_approval: bool`。

---

## 1. 一个布尔会产生三种失败

把"要不要审批"写成工具级布尔，只有两个极端：**每次都问**，或者**完全不问**。三种典型场景各自撞墙：

| 场景 | 布尔给出的结果 | 实际后果 |
|---|---|---|
| 代码密集型任务（写→跑→报错→改→再跑） | 每次调用都停 | 反复打断，人疲于点同一张卡；点久了就会无脑点 |
| 只读探查类工具 | 要么每次问（烦），要么标成不问 | 标成不问之后，同一工具一旦被用于写操作也没人拦 |
| 无人值守 / 作为库被集成 | 标了需审批却没人可审 | **任务永久停住**：进程活着、日志干净、不结束 |

前两种是体验问题，第三种是正确性问题。三者共同的根因是：**用一个静态的、工具级的布尔，去回答一个
动态的、按调用变化的问题。**

## 2. 判据：两个问题

```
对这一次调用：
  ① 动作可逆吗？          只读 / 纯计算 / 沙箱内执行        → 可逆
                          写线上 / 对外发送 / 删数据 / 花钱  → 不可逆
  ② 出事了有机制兜住吗？    沙箱可用 / 权限层已拦 / 可回滚   → 有
                            都没有                        → 没有

  两个都"是" → 自动放行        任一为"否" → 问人
```

**判据是"这次动作有什么后果"，不是"属于哪个领域"。** 按领域判会得出荒谬结论：风控领域里一个纯查询
的插件凭什么要审批？数据分析领域里一句 `DROP TABLE` 难道因为"是数据分析"就放行？

可逆性回答"做错了能不能收回"，兜底机制回答"就算判断错了，损失被什么限制住"。两者都指向同一个问题：
**这个动作出错时的代价边界在哪里。**

## 3. 三档决策

| 档 | 含义 |
|---|---|
| `AUTO` | 不问，直接放行 |
| `ASK` | 停下来等人（人工审批） |
| `DENY` | 不问，直接拒绝 —— 风险达到**部署方配置的拒绝线** |

**`AUTO` 附带硬前提**（见 §3.3），不满足则强制降级为 `ASK`。

`DENY` 与 `ASK` 的区别不是"更危险"，而是"**不该由人批**"：领域包只能把某次调用声明为
红线档（`CRITICAL`），是否真的拒由**部署方**那条拒绝线决定 —— 红线是部署配置，不是领域包
写死的。默认只有红线档会触发 `DENY`；部署方可以调低这条线。

### 3.1 策略挂载层级

| 层级 | 回答的问题 | 用途 |
|---|---|---|
| 部署级 | 这个部署有没有人审？ | 交互式部署逐次问；无人值守部署需要显式策略 |
| 领域包级 | 我这个领域的工具默认怎么审？ | 领域自带的默认态度 |
| 工具级 | 这个工具要不要审？ | 静态兜底 |
| **调用级** | **这一次调用的参数** | **真正的判定粒度** |

调用级是关键：让人疲惫的不是"要审"，是"每次都审"。同一把 `code_executor`，"只读聚合"与
"装包 + 发网络"的风险完全不同，只有看参数才分得开。

### 3.2 领域包注册风险策略

框架提供机制，领域包提供策略 —— 与"框架侧不出现领域名"是同一条原则的延伸。
领域包在注册工具时可附带一个风险策略：

```python
def risk_of_code_execution(args: dict) -> str:
    """只回答"多危险"；"多危险才问人"由部署策略决定。"""
    code = str(args.get("code") or "")
    if any(k in code for k in ("requests.", "urllib", "socket", "subprocess", "pip install")):
        return "HIGH"
    return "LOW"
```

- **不提供策略 → 默认一律按需审批**（保守，与"没有这个机制"时的行为一致）；
- 策略只做**分类**，不做**放行决定**。分类器与阈值策略分开，各自可替换 —— 调保守程度不必改分类逻辑，
  换判断方式不必动策略；
- 风险取值 `LOW / MEDIUM / HIGH / CRITICAL / UNKNOWN`；**`UNKNOWN` 按需审批处理**（未知不放过），
  **`CRITICAL` 由部署方的拒绝线决定是否直接拒**（默认直接拒）。

### 3.3 自动放行必须以"机制兜底"为前提

> **自动放行的理由必须是"有机制保证安全"，不能是"我判断它安全"。**

这是本设计最硬的一条约束。判定函数本身也是代码，**它会错**：基于关键词或正则的风险分类，绕过它
只需要换一种写法。因此 `AUTO` 档必须同时满足：

- 该工具**运行在可强制隔离的沙箱中，且沙箱当前可用**；或
- 存在**等价的确定性兜底**（权限白名单已经拦住了不该碰的、操作本身可回滚）。

不满足则**强制降级为 `ASK`**。

这条约束的推论很直接：**一个没有沙箱的高危工具，无论风险分级多低都不自动放行。** 反过来，
自动放行"沙箱内跑代码"之所以成立，唯一理由是它无论如何都进沙箱 —— 自动审批省掉的只是人眼，
安全仍由沙箱边界兜着。

### 3.4 无人值守时的两个问题，两个配置

"停下来等人"在有人值守时是功能，在无人值守时是缺陷 —— 如果没有任何非人触发的判定点，
**没人处理的审批会让任务永远停住**。这里其实是两个不同的问题，必须分开回答：

#### 问题①：这个部署**有没有**审批通道？

| 配置 | 含义 | 存在需审批工具时 |
|---|---|---|
| **不配置** | 没回答过 | **启动即失败**（错误信息给出下面两个选项） |
| `http` | 有人审（服务端审批端点） | 正常 |
| `none` | 明确无人值守 | **启动即失败**：与"存在需审批工具"自相矛盾 |

**不设默认值** —— 理由与"没有凭据就不该对外提供服务"完全同源：**默认值一旦存在，就等于没人
回答过这个问题**。这道检查的价值不在拦住谁，而在**强迫部署者把"这个部署有没有人审"明确说出口**。

它同时把"将来会不会有人来审"这个**不可知**的问题，换成了"有没有接审批通道"这个**可声明**的
配置事实 —— 二者必须分清：没人能预测人会不会来，但有没有接通道是可以声明的。

#### 问题②：有通道，但**一直没人应**怎么办？

| 模式 | 行为 |
|---|---|
| `auto_reject`（默认） | 超过时限仍无人处理 → 自动转"驳回"并推进，任务不会停住 |
| `block` | 一直等人；选择它时**启动打 WARNING**（让"我要一直等人"成为一个被说出口的选择） |

**"以为开了审批、实际没人审"是最坏的状态** —— 它同时失去安全（没人看）与进展（任务停住），
且从表面看不出来。以上两条配置合起来防的正是它：先逼你回答"有没有人审"，再保证回答了之后
不会静静卡死。

### 3.5 可见性

`AUTO` 是一次**静默放宽**，比 `ASK` 更需要留痕。每一档都上报一条管控裁决事件并落审计，带上
风险等级、命中的策略、以及靠哪个机制兜底。**管控可见性的定位是"一旦发生必须可见"，不是"常态刷屏"**
—— 自动放行恰好属于"一旦发生必须可见"这一类。

### 3.6 与"业务审批"的边界

有两类东西看起来都是"停下来等人点"，但归属完全不同：

| | **安全审批** | **业务审批** |
|---|---|---|
| 问的是 | Agent 要执行这个动作，**允许吗** | 这份合同，**法务签不签** |
| 归属 | **harness 的安全层** | **领域包的业务流** |
| 没有它会怎样 | 可能执行被注入的恶意动作 | 业务走不下去 |

本文只覆盖**安全审批**。业务审批（质量门人工复核、签署一类的流程节点）属于领域包，由领域包自己
声明与实现 —— 把它塞进安全层会让模型错位：安全层管的是"Agent 能不能做"，业务层管的是
"这件事在流程上该不该往下走"。

## 4. 设计问答

**Q：用 LangGraph 之类的图框架自建时没见过这个问题，它是不是只在桌面端/CLI 才出现？**

不是。图框架提供的是 `interrupt()` —— 一个"暂停并把控制权交回调用方"的原语，**它不含审批语义**：
不知道谁该点、要不要再问、有没有常驻决定。问题不来自框架，来自三个条件同时成立：① 某工具被标为
需要审批；② 同一任务内它被调用不止一次；③ 循环里有一个人。拆掉任一条，问题消失 —— 所以它在
"把高危工具放进循环里"的任何形态下都会出现，与界面是终端、桌面还是网页无关。

**Q：如果是作为库被集成（没有自己的界面），审批卡片在哪里看到、在哪里同意？**

库**不弹任何东西**。它只交出一个暂停的执行现场和一份载荷；把载荷怎么呈现、决定怎么收回来，
完全是集成方的事。最小形态就是两行：

```python
print(f"需要批准：{req['tool']}\n{req.get('arguments')}")   # ← 你决定"在哪看到"
ans = input("批准？[y/N] ")                                # ← 你决定"在哪同意"
```

把它换成 HTTP 接口 + 前端卡片，就是 Web 控制台；换成 Slack 消息，就是 IM 里的 Agent；
换成工单系统，就是企业审批流。**库给的是"停住并保住现场"的能力，接人的那一层是应用的活。**

**Q：一运行就卡住，合理吗？**

不合理，而且这是本设计存在的直接原因之一。需要区分两件事：**"停下来等人"是功能**，
**"没人可等却静默地一直等"是缺陷**。前者是人工审批本身，后者说明缺少 §3.4 那类落地行为。
一个可用的 harness 至少要让"有人正等你回话"这件事有出口（状态、事件、时限），
否则集成方会以为是自己写错了。

**Q：既然没人审，那这道门还有必要生效吗？**

在无人值守场景下，**一道需要人的闸门不该生效** —— 它的安全价值完全建立在"有人会看"之上，
没人看时它提供不了安全，只提供堵塞。但"关掉审批"不等于"放弃安全"：安全责任应当**显式转移给
不需要人的那几层** —— 隔离沙箱（不可用即 fail-closed）、权限白名单（模型看不到越权工具）、
审计留痕（事后可追溯）。审批是这几层的**补充**，不是它们的替代。

**Q：能按领域包、按任务配不同的策略吗？**

能，而且这正是把策略下沉到领域包的理由。挂在四层：部署级（有没有人审）、领域包级（本领域默认
态度）、工具级（静态兜底）、**调用级（看这一次的参数）**。任务也可以在创建时带一个档位
（例如"只读分析"与"变更申请"），由框架据此选择策略。

**Q：同样的"停下来等人"，那合同审批算不算同一回事？**

不算。合同审批是**业务审批** —— 它要求人签署，是因为业务本身要求人签署，与 Agent 的安全无关。
两者常常长得一样（都是停下来等人点），但归属、责任人和失效后果都不同（见 §3.6）。
把它们混成一层，会导致用"安全"的名义去驱动业务流程，或者反过来用"业务"的名义绕过安全检查。

## 5. 与主流框架的对照

| | 默认行为 | 显式的"不问"路径 | 无人时谁兜底 |
|---|---|---|---|
| OpenAI Agents SDK | `needs_approval` → 暂停并返回待批项 | `on_approval` / `on_approval_request` **回调**（返回即继续） | 回调内的策略 |
| OpenHands | `ConfirmRisky`：低/中风险自动放行，高风险要问 | `NeverConfirm` / 调阈值 / 未知项处理 | LLM 风险分类器 |
| Codex | `on-request`：模型自行决定何时问 | `approval_policy=never`；**无人值守默认即 `never`** | **显式转给 OS 沙箱** |
| Claude Code | 逐次弹提示 | 会话级"总是允许" / 持久权限规则 | 沙箱 + 权限规则 |

三点共识与本设计一致：

1. **默认都是"停下等人"，没有框架会替调用方自动批** —— 所以"一运行就等"是行业默认行为，
   需要的是把它变成**可配置**的，而不是取消它；
2. **每家都提供一条显式的"不问"路径**，且都由调用方决定策略 —— 与 §3.2 的分工一致；
3. **风险分类与放行策略分开**（OpenHands 最清楚：分析器只回答"多危险"，策略回答"多危险才问人"），
   以及 **无人值守时把安全显式转给沙箱**（Codex 说得最直白）。

## 6. 不做

- **业务审批流**（工单、多级会签）：属于领域包的业务能力，不进安全层（见 §3.6）；
- **用另一个模型充当审批者**：引入"自动审批者本身也要被约束"的问题，
  在明确的约束设计出现前不做；
- **风险等级的全局默认阈值表**：先让各领域自行声明；出现多个领域重复定义同一阈值时再抽公共默认。
