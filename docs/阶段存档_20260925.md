## 6. 关键架构决策（已拍板，勿再反复）

### 6.1 本轮新增的决策

1. **沙箱用 OpenSandbox，不手写 Docker 隔离**。
   理由：符合「尽量借鉴成熟开源框架」；自带 Command/Filesystem/Code Interpreter 环境、网络策略、凭证保险箱、gVisor/Kata/microVM 可插拔运行时。
   **服务端锁定 0.2.3**：1.1.0 的 PyPI wheel **缺 `services/fast_sandbox/generated/` protobuf 包**，启动即 `ModuleNotFoundError`，不可用。
2. **沙箱服务端独立 venv**，不污染项目 `.venv`（服务端依赖 docker/fastapi/grpcio/kubernetes/psycopg 等重依赖）。
3. **双层文件访问平面 = 主机 VFS ↔ 沙箱私有 FS，经 SDK Filesystem API 显式搬运，禁止 bind mount**（`allowed_host_paths = []`）。比挂载更严格，且每次跨平面读写都是可拦截/限额/审计的咽喉点。
4. **保留 egress sidecar**。它是 FQDN 级出网管控 + 凭证保险箱的承载点，属企业级必要能力；即使当前 `code_executor` 用不到，也不为省启动开销而裁剪（**勿以"当前定位不需要"为由简化架构**）。
5. **沙箱失败一律 fail closed**，宿主上不存在进程级回退路径。
6. **`tool_mode` 是框架级配置**（`AGENT_TOOL_MODE`），不是示例私有开关。取值 `react` | `native`。
7. **FC 的批量 tool_calls 按序执行**，不真并行 —— 限流是工具维度滑动窗口、审计要保序、沙箱有并发上限，并行会破坏这三者的确定性。
8. **MCP 双向都要，管控不绕过**：Server 方向暴露的工具仍经 `broker.invoke` 执行，PDP/校验/限流/沙箱/审计对 MCP 客户端同样生效。

### 6.2 沿用上一份存档的决策（仍然有效）

- 执行范式：顶层 Plan-and-Execute + 每个子任务内 ReAct。
- 质量门五处置 PASS/RETRY/REPLAN/HUMAN/FAIL；Critic 故障 fail-open 保留硬校验。
- 工具与协议解耦：一份工具可被 ReAct / FC / MCP 三协议复用，最终归一 `broker.invoke(name, args)`。
- **绝对导入**：新模块统一 `from harness.xxx` / `from tools.xxx`。
- 内置工具保持**通用**，不写 IV/WOE/KS/PSI 等风控专有指标。

### 7.1 人工审批机制缺口（重要）

**图上要求**：「安全沙箱……对代码执行、Skill 调用等高风险动作进行沙箱隔离，**结合人工审批机制**保障线上规则变更与灰度发布的安全合规。」

**实际状态：`requires_approval` 只有声明，没有强制力。** 全代码库只被读两处：
- `tool_broker.py:70` —— 在**给 LLM 看的工具清单文本**里加一句"注意：此工具需要人工审批"（**纯提示词**）
- `tool_broker.py:326` —— 往审计里记 `approval_required=true`（**只是记录事实**）

`ToolBroker.invoke` 的九步流程（中间件→存在性→PDP→参数→限流→**执行**→after钩子→记时间→审计）**没有审批这一步**。
`orchestrator.human_node` 的 `approval_callback(task, result)` 是**子任务级**（审批一个已完成的 SubAgentResult），与工具级审批是两件事，且只有 gate 判 HUMAN 时才走到。

**后果**：`code_executor` 标了 `requires_approval=True`，模型被"告知"需要审批后照常调用，broker 直接执行、沙箱直接跑、审计记下"本次需要审批"—— **而审批从未发生**。实证：`tests/_smoke_tools.py` 里 `broker.invoke("code_executor", …)` 一路成功，全程无审批环节。

**已决定：直接做层次二，不做临时版。**

- **层次二（正确形态）**：审批 = **挂起-恢复**，而非同步回调。图为佐证——记忆那条写着「Redis 保存短期对话历史、任务计划、**审批断点**和临时数据」。链路：高风险动作 → 挂起并落 LangGraph 检查点 → 持久化审批断点 → 人类决策（经 HTTP API）→ 恢复执行。
- **实现方式（2026-09-25 拍板）**：**采用 LangGraph `interrupt`，不自研挂起-恢复。**
  理由：interrupt 是**本项目已在用的编排引擎自身能力**（同源），且与 checkpointer 天然配套 ——
  自研等于从零重造 LangGraph 已有的挂起-恢复 + 检查点，还要自己做状态序列化、恢复点、并发。
  且审批目前**没有任何自研模块可"保留"**，不涉及"换掉自研动摇定位"的问题。
  **顺带把闲置的 checkpointer 用起来**（它此前只作为参数存在，从未传入或跑过）。
  同批拍板：**PDP 与记忆三层维持自研**，不替换为 OPA / Mem0（见《项目计划.md》§0.1 C4）。
- **为何不做层次一**（在 invoke 里插一个同步审批回调的最小闸门）：**没有 HTTP API，审批人无处下决策**，临时闸门只能靠测试桩验证，会围绕一个将被替换的形态调优报错，**导致目标偏移**。用户明确要求不为"临时可测"降低完成质量。
- **落地时点**：与 #19 服务化同期；依赖 #13（审批断点持久化到 Redis）。

### 7.2 沙箱服务端的部署位置（**属阶段0 基础设施编排，非新增交付物**）

**曾误判**：一度把"写 start/stop/status 生命周期脚本、注册 Windows 服务"当成待办 —— 那是**凭空发明的交付物，计划里没有**。核对计划后结论如下。

计划给 infra 生命周期指定的机制是唯一的 —— **docker-compose**：

| 计划出处 | 原文 |
|---|---|
| 交付物表 | 基础设施编排（infra/）｜**docker-compose**：Redis+Milvus+Kafka+MinIO |
| 目录结构 | `infra/docker-compose.yml` |
| 阶段0 任务表 | `infra/docker-compose.yml`｜Redis+Milvus+Kafka+MinIO+Zookeeper 编排 |
| 阶段0 验收 | **`docker-compose up -d` 启动所有基础设施** |

→ 沙箱服务端应**补进 `infra/docker-compose.yml`**，与其它基础设施同一机制
（`up -d` / `ps` / `logs` / `down`），**不另立脚本**。

**为何计划原本没有它**：阶段4 原文是「`harness/sandbox/isolator.py`｜隔离机制：Docker 容器创建/销毁」——
原假设是**手写 Docker SDK**，不存在"服务端"这个组件。OpenSandbox 是为对齐参考设计而引入的（见 §6.1），
其服务端是**计划未预见的新基础设施组件**，属**对计划的修订**，应记入计划（已同步至《项目计划.md》阶段0），
而非在存档里外挂一条。

**修订到 compose 的两个前提（待拍板）**：
1. 官方**不发 server 镜像**（只发 `execd` / `egress`）→ 需自建 `infra/Dockerfile.opensandbox-server`
   （pip 装 `opensandbox-server==0.2.3` 后启动；**注意 1.1.0 打包坏了**，见 §6.1）
2. 服务端**必须挂 Docker socket** —— 它要建沙箱容器，这是它的固有权限边界，投产前需明确接受

**当前过渡状态**：`infra/opensandbox-server/start.ps1`（前台启动 + 独立 venv）。
这是**临时可用形态，不是最终部署方式** —— 最终形态是纳入 compose。

### 7.3 配置层的机器相关写死值与凭据处理（**随 §7.2 一并解决，勿单独提前修**）

**严重度如实**：① 是本地开发用固定串、服务仅监听 `127.0.0.1`，**实际风险低**，但对自称企业级的 harness，这个**模式**本身错误 —— 讽刺的是 `.env` 被 gitignore，而 key 的默认值却写进了 `config.py` 与 `.env.example`，等于绕过自己的忽略规则。

**为何不现在修**（一致性要求）：**"删除写死值"不依赖任何东西，但"换成什么注入机制"是彻头彻尾的部署决策** ——
服务端现在是裸进程 + toml（key 只能写 toml 字面量或环境变量）；纳入 compose 后则变为 compose
`environment:` / `env_file:` / docker secret；甚至"本地开发不设 key、走 insecure"也是部署选择。

绝对路径那条更直接：state 到底挂卷还是用命名卷，属于同一个待拍板决策。

### 8.2 本项目踩过的坑（都是真跑撞出来的）

| 现象 | 根因 | 处置 |
|------|------|------|
| `.env` 改了没用，配置恒为默认值 | pydantic-settings 的 `env_file` **不传播到嵌套模型** | `config.py` 顶部显式 `load_dotenv(项目根/.env)` |

| `422 unknown variant 'tool_call', expected 'function'` | LangGraph 把消息转成 LangChain 形态，其 `tool_calls` 条目 `type="tool_call"`、`args` 是 dict | `nodes._normalize_tool_calls` 统一成 OpenAI 契约 |

| `Egress sidecar did not become ready within 30s` | 高频连续建沙箱时 sidecar 起不来 | `sandbox.toml` 的 `readiness_timeout_seconds` 30 → 120 |
| 沙箱里 `Cannot save file into a non-existent directory` | 镜像无 `/home/sandbox/{in,out}` | 改用 Filesystem API 建目录（换任何镜像都成立） |
| 沙箱超时被误判为普通失败 | 被强杀的进程**没有** `execution.complete` | 改量测 `commands.run` 自身耗时窗口 |
