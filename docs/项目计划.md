# ETL-Harness 工业级开发计划

> 基于 LangGraph 编排引擎 + 手写 Harness Engineering 管控层的企业级 Agent 框架。
> 完整实现：任务规划、虚拟文件系统、子 Agent 委派、上下文管理、可插拔中间件、Skills 技能系统、全生命周期记忆、安全沙箱、链路追踪、FastAPI 服务化。

## 一、项目目标

### 1.1 总体目标

构建一个工业级 Agent Harness Engineering 框架，具备企业级 Agent 开发所需的完整管控能力：

| 能力域 | 具体能力 |
|--------|---------|
| **任务规划** | 复杂目标拆解为子任务，pending/in_progress/completed/failed 状态追踪，Redis 持久化 |
| **虚拟文件系统** | /workspace /reports /logs /policies /memories 目录抽象，文件读写/编辑/搜索/版本留痕，MinIO 后端 |
| **子 Agent 委派** | 主 Agent 委派专业子 Agent，独立上下文执行，仅返回结构化结论 |
| **上下文管理** | 大结果沉淀到 VFS，prompt 只保留摘要+文件链接，减少 Token 消耗 |
| **可插拔中间件** | 模型调用/工具调用/文件读写/任务状态变更节点注入 Hook，支持缓存/重试/PII检测/权限校验 |
| **Skills 技能系统** | 模板/SOP/Prompt/领域文档/SQL模板/脚本打包为可复用 Skill，渐进式披露 |
| **全生命周期记忆** | Redis 短期记忆 + Milvus 长期向量记忆 + 工作记忆，跨会话恢复 |
| **安全沙箱** | Docker 容器双层隔离，网络/进程/文件系统隔离，高风险动作沙箱执行 |
| **链路追踪** | 全链路埋点，Kafka 上送，执行链路可视化 |
| **工具管控** | Tool Broker 统一入口，参数校验/限流/异常兜底/审计 |
| **权限管控** | PDP 策略决策点，细粒度权限判断 |
| **ReAct 引擎** | LangGraph 状态图编排，think/action/final 循环 |
| **断点恢复** | LangGraph Checkpointer，每步状态持久化 |
| **服务化** | FastAPI+ASGI 高性能服务，同步/流式 API |

### 1.4 智能体执行范式：Plan-and-Execute 外壳 + ReAct 内核

本项目**不采用单一循环**，而是分层组合两种范式：

- **顶层 = Plan-and-Execute（规划-执行）**：面向 ETL/数据分析"流程骨架清晰、步骤多、需全局覆盖与可恢复"的特点。Planner 先把目标拆成有序、带依赖的 `TaskPlan`；Dispatch 逐个取出子任务；每个子任务交给执行体；全部完成后 Synthesize 汇总；执行偏离/失败时回到 Planner **Replan**。
- **执行体 = ReAct 内核（think→action→observation）**：单个子任务内部，具体调哪些工具、参数是什么，要根据中间结果见机行事，因此保留 ReAct 的探索灵活性。

> 一句话：**宏观用 Plan 保证方向与覆盖（确定性骨架），微观用 ReAct 应对每步不确定性（探索性执行）。** 这也是工业界 "Plan-and-Execute with ReAct workers" 的主流形态，与"任务规划 + 子 Agent 委派"模块对应。

```
START → Planner ──(Replan)──┐
          │                 │
          ▼                 │
       Dispatch            │
          │                 │
          ▼                 │
   ┌───────────────┐        │
   │ Executor 子图  │        │  每个子任务独立小上下文
   │ think⇄action   │        │  （ReAct，复用 nodes/graph）
   └───────┬───────┘        │
           ▼                │
       StepDone ──还有任务?─┘
           │全部完成
           ▼
       Synthesize → END
```

| 架构角色 | 模块 | 复用模型 |
|---------|------|---------|
| Planner / Replanner | `planning/planner.py`、`planning/task_store.py` | `TaskPlan` / `TaskStep` |
| ReAct 执行内核（子图） | `nodes.py`（think/action/route）、`graph.py`（`build_executor_graph`） | `ThoughtStep`、`AgentState` |
| 顶层编排 + 子 Agent 委派 | `orchestrator.py`（plan→dispatch→execute→replan→synthesize） | `SubAgentDef` / `SubAgentResult` |
| 断点恢复 | LangGraph Checkpointer + TaskStore | `TaskStep` 状态 |

## 七、数据分析工具详细设计（分析角度规划）

> 所有工具统一遵循契约：**一个 `ToolDef`（说明书，`parameters` 为标准 JSON Schema）+ 一个 `handler(args, context) -> (ok: bool, text: str, artifacts: dict)`**。
> 工具内部不出现任何 ReAct / Function Calling / MCP / OpenAI 字样——调用协议由上层 nodes 决定，工具只负责确定性的数据处理，因此**一份工具可同时被 ReAct、Function Calling、MCP 三种方式复用**。
> 产物统一落 VFS：清洗后数据进 `/workspace`，报告与图表进 `/reports`；ContextManager 只把摘要 + 文件链接喂回 LLM。

### 7.0 工具编排主链路

```
data_inspector  →  data_cleaner  →  eda  →  chart_generator  →  code_executor
  （体检/认识数据）   （清洗/产出干净集） （统计/找规律）  （可视化关键发现）  （兜底/自定义深度分析）
                                                                 ▲
sql_query（数据库场景）：数据源是 DB 而非文件时，用 NL2SQL 替代前 3 步的文件读取路径
```

每一步的结构化产物都写入 VFS 并登记版本，LLM 的上下文里只保留"结论摘要 + 文件链接 + 下一步建议"。

### 7.1 data_inspector（数据体检 / 探查）

- **定位**：Agent 拿到任意数据文件后的第一步，建立对数据的整体认知并标记风险。
- **输入参数**：`file_path`（必填）、`sheet`（Excel）、`encoding`、`sample_rows`（抽样行数，默认 10000）。
- **分析角度**：
  | 维度 | 具体内容 |
  |------|---------|
  | 文件层 | 格式（csv/excel/parquet/json）、文件大小、编码、分隔符、sheet 列表、是否含表头 |
  | 结构层 | 行数、列数、内存占用、完全重复行比例 |
  | Schema 层 | 每列：列名、推断 dtype、**业务类型推断**（数值/类别/时间/文本/布尔/ID）、非空数、缺失率、唯一值数 |
  | 样例层 | head N、tail N、随机抽样 |
  | 风险标记 | 全空列、常量列、高缺失列（>50%）、疑似主键/ID 列、疑似目标列（label/y/target）、疑似时间列 |
- **输出**：text 给一句话体检结论；artifacts 含 `schema`（字段表）、`quality`（质量概览）、`risks`（风险清单）、`sample`。
- **管控属性**：role=analyst，只读，限流 30/min，无需沙箱。

### 7.2 data_cleaner（数据清洗）

- **定位**：根据体检结果对数据做可追溯的清洗，产出"干净数据集 + 清洗报告"。
- **输入参数**：`file_path`（必填）、`rules`（清洗策略 dict，可缺省由工具先给建议）、`output_name`。
- **分析/处理角度**：
  | 类别 | 策略选项 |
  |------|---------|
  | 缺失值 | 删除行/列、均值、中位数、众数、前后向填充、插值、指定常量；按列缺失率给推荐策略 |
  | 重复值 | 整行去重、按主键/指定列去重 |
  | 类型修正 | 字符串转数值/日期，剥离货币符号/千分位/单位，百分比转换 |
  | 异常值 | IQR / Z-score 检测；截断、Winsorize 缩尾、或仅标记不删除 |
  | 文本规范 | strip、全半角统一、大小写、连续空白折叠、空字符串转 NaN、类别同义词归一 |
  | 列处理 | 删除全空/常量列、列重命名、保留/排序列 |
- **输出**：清洗后文件（写 `/workspace`，VFS 留版本）、**清洗报告**（每列应用了什么规则、影响多少行、前后缺失率对比）。
- **管控属性**：role=analyst（写 workspace），限流 20/min。

### 7.3 eda（探索性统计分析，核心工具）

- **定位**：从统计角度系统挖掘数据规律、异常与变量关系，是分析深度的主要载体。
- **输入参数**：`file_path`（必填）、`target`（可选目标列 y）、`group_col`（可选分组列）、`columns`（分析范围）。
- **分析角度**：
  | 类别 | 分析项 |
  |------|--------|
  | 总览 | n×p、内存、数值/类别/时间列分组、整体缺失情况 |
  | 单变量·数值 | count/mean/median/std/min/max、四分位数、IQR、偏度 skew、峰度 kurtosis、变异系数 CV、0 值占比；直方图分箱频次、长尾判断 |
  | 单变量·类别 | 基数 cardinality、众数及频次、Top-N 频次表、稀有类别占比、类别熵 |
  | 单变量·时间 | 起止时间、跨度、粒度推断、缺失日期、趋势/周期/季节性初判 |
  | 双变量 | 数值×数值：Pearson/Spearman 相关系数、高相关变量对；类别×数值：分组均值/中位数对比、组间差异；类别×类别：交叉列联表 |
  | 目标关系（指定 y 时） | 数值目标：各特征相关性排序；类别目标：分组差异/类别分布对比；特征区分度初判 |
  | 异常检测 | 各数值列基于 IQR 的离群点计数与占比 |
  | 业务汇总 | 关键指标聚合、分组 Top 排名 |
- **输出**：统计字典 artifacts（`stats`/`corr`/`group_stats`/`outliers`/`findings`）、Markdown 分析报告（写 `/reports`）、text 列出 3~5 条关键发现。
- **管控属性**：role=analyst，只读，限流 20/min。

### 7.4 sql_query（NL2SQL 数据查询）

- **定位**：数据源是结构化数据库（SQLite/连接串）而非文件时的查询入口，与文件型分析互补。
- **输入参数**：`data_source`（sqlite 路径或连接名）、`question`（自然语言，二选一）或 `raw_sql`（直接给 SQL）、`limit`。
- **分析角度/能力**：列出库表与 schema、表行数与样例值；基于 schema + 样例值由 LLM 生成 SELECT；**回显生成的 SQL 供核对**。
- **安全约束（重点）**：只允许 `SELECT/WITH`，禁止 `DROP/DELETE/UPDATE/INSERT`；自动强制 `LIMIT`；查询超时；只读账号。
- **输出**：结果列、结果行（截断）、总行数、执行时长、实际执行的 SQL。
- **管控属性**：role=analyst，只读，限流 30/min，建议走沙箱网络白名单。

### 7.5 chart_generator（可视化）

- **定位**：把统计发现转成图表，按"分析目的 × 字段类型"自动选型。
- **输入参数**：`file_path`、`chart_type`（可 `auto`）、`x`、`y`、`group_by`、`title`、`output_name`。
- **图表选型矩阵**：
  | 目的 | 字段 | 图表 |
  |------|------|------|
  | 分布 | 单数值 | 直方图 / 箱线图 |
  | 构成 | 单类别 | 条形图（频次）、占比条形（类别少时） |
  | 关系 | 数值×数值 | 散点图（可加趋势线） |
  | 对比 | 类别×数值 | 分组柱状图 / 分组箱线图 |
  | 趋势 | 时间×数值 | 折线图 |
  | 交叉 | 类别×类别 | 堆叠柱状 / 交叉热力图 |
  | 相关 | 多数值 | 相关系数热力图 |
  | 缺失 | 任意 | 缺失率条形 / 缺失矩阵 |
- **输出**：PNG（写 `/reports/charts`，处理中文字体）+ 文件路径；text 写明图表结论。
- **管控属性**：role=analyst，限流 20/min，依赖 matplotlib。

### 7.6 code_executor（代码沙箱执行，兜底工具）

- **定位**：前 5 个工具覆盖不了的自定义分析，由 LLM 编写 pandas/numpy/python 代码在隔离环境中执行。
- **输入参数**：`code`（必填）、可用数据路径（由 context/VFS 注入）。
- **机制**：预置 pandas/numpy/matplotlib；数据目录只读挂载；捕获 stdout、最后表达式结果、生成文件；超时与内存/网络限制；失败时把 traceback 回灌 LLM 自修（Reflexion）。
- **输出**：stdout、结果摘要、产物文件路径。
- **管控属性**：**`run_in_sandbox=True`、role=senior_analyst、限流 5/min、最高审计级别**（唯一执行任意代码的工具）。

## 八、后续演进方向（Function Calling 与 MCP）

> 主线先用 ReAct 跑通端到端 MVP；以下为达到工业完整性的演进项，**不改动已写好的工具与 ToolBroker**。

### 8.1 原生 Function Calling（双模式工具调用）

- **现状**：主线 ReAct（`list_tool_descriptions()` 拼文本 + `LLMClient.chat_json` 解析 JSON），模型无关、过程可见；`list_tools_openai_format()` 已能生成 OpenAI tools 结构但尚未接线。
- **演进工作**：
  1. `llm_client.py` 增加支持 `tools` / `tool_choice` 参数的对话方法，读取 `message.tool_calls`、回传 `role="tool"` + `tool_call_id`；
  2. `nodes.py` 增加 Function Calling 节点（或在节点上加 `tool_mode="react" | "native"` 开关）；
  3. 复用同一套 Broker 与工具，最终都归一化到 `broker.invoke(name, args)`。
- **收益**：工具调用格式由 API 保证、更稳定；支持一次返回多个 `tool_calls` 并行执行；生产环境更可靠。
- **原则**：ReAct 用于教学/调试/兼容弱模型，Function Calling 用于生产，二者可切换、可 A/B 对比。

### 8.2 MCP（Model Context Protocol）工具协议接入

- **定位澄清**：MCP 属于**工具接入/传输层**（跨进程、跨语言、远程工具的标准发现与调用协议），与 ReAct/Function Calling（模型决策层）**不冲突、不二选一**——MCP 负责把外部工具取回来，取回后仍由 ReAct 或 FC 让模型决策。
- **演进工作（新增 `harness/mcp_adapter.py`）**：
  - **方向 A · 作为 MCP Client（优先）**：连接外部 MCP Server（数据库、文件系统、内部 API 等），通过协议 `tools/list` 拉取远程工具清单，把每个远程工具**包装成符合 `ToolHandler` 签名的本地 handler**（内部走 MCP 调用），再 `broker.register(...)`。对上层完全透明，模型无感知工具在远程。
  - **方向 B · 作为 MCP Server**：用 FastMCP 把 ToolBroker 已注册工具暴露出去，供 Claude Desktop、Cursor 等 MCP 客户端调用。
- **收益**：工具生态可插拔、跨语言复用，框架从"自带工具"升级为"可接入任意 MCP 工具生态"。

### 8.3 其他可选增强

多模型路由与降级、Embedding 客户端补全、全异步化（async tool / httpx）、执行链路可视化 UI、Milvus Lite / 本地 Kafka 队列等开发环境轻量回退。
