### ⚠️ C1 · VFS 目录方案

| | 方案 |

- **信息来源 B**：`harness/config.py` 的 `vfs.default_directories`，且磁盘 `data/vfs/` 下已全部建好。
- **分歧本质**：来源 B 的目录集从风控版沿用（`/policies` 是策略 DSL 语义，与数据分析无关）；来源 A 是数据分析语义，且把工作区**按处理阶段细分子目录**（raw→cleaned→scripts→charts）。
- **影响面**：VFS 配置、全部工具的产物落盘路径、各子 Agent 的读写约定、示例与测试断言。
- **待拍板**：采用来源 A（需迁移路径与改工具）／来源 B（需去掉 `/policies` 这类无关目录）／混合。

#### C1 建议方案（**已决定暂缓** 2026-09-25）

> **已决定：先不改，后续再决定。** 维持现状目录方案
> （`/workspace`、`/reports`、`/logs`、`/policies`、`/memories`）。
> 下文建议方案**保留备查**，待后续需要时再启用。
> 注：`/logs`、`/policies`、`/memories` 三个空壳目录**暂留原样**（无功能影响，仅占位）。

**实测事实**（决定了这个决策比看上去简单）：

| 目录 | 代码/测试/示例中被引用 | 结论 |
|---|---|---|
| `/workspace` | 10 处 | ✅ 真在用 |
| `/reports` | 18 处 | ✅ 真在用 |
| `/logs` | **1 处** | ⚠️ **空壳** |
| `/policies` | **1 处** | ⚠️ **空壳**（且是风控遗留） |
| `/memories` | **1 处** | ⚠️ **空壳** |

> `/logs` `/policies` `/memories` 的那 1 处引用**都是"定义本身"**（`config.py` 的 `default_factory` + `vfs.py` 的 docstring 说明），
> **没有任何工具、测试、示例读写它们**。即：定义了、建了目录、但无人使用。

**建议：取来源 A 的语义分层，但图表留在 `/reports`**

```
/workspace/raw        原始数据（只读来源）
/workspace/cleaned    清洗后数据
/workspace/scripts    执行过的代码（配合 C3「生成代码留档」，见下）
/reports/final        最终报告
/reports/charts       图表产出
```

理由：
- **按处理阶段细分 `/workspace`** 采纳（来源 A 的做法语义更清晰，也让子 Agent 的读写约定更明确）
- **图表归 `/reports/charts` 而非来源 A 的 `/workspace/charts`** —— 图表是**产出物**不是**工作数据**；且现状 `/reports/charts` 已有 18 处引用，改动面为零
- **删除 `/policies`** —— 风控遗留，数据分析无归属
- **删除 `/logs`** —— 系统日志现走 `data/audit/*.jsonl`（审计）与 logging，VFS 里这个目录无实际用途
- **删除 `/memories`** —— 记忆已走 Redis/Milvus **真实后端**（已实测接通），VFS 不该重复承载一份
- 代价：需改 `vfs.default_directories` + 各工具的落盘路径 + 测试/示例断言

#### C2 建议方案（**已拍板** 2026-09-25）

> **已定：8 个** —— 新增 **QA/质检 Agent**；保留 `coder` 与 `executor`；**暂不新增「数据接入」角色**。
>
> 「数据接入」为何暂不新增：现有 `inspector`（文件接入与探查）+ `analyst`（`sql_query` 数据库接入）
> 已覆盖当前的数据接入需求；C5 首期虽扩到多数据库，但 `sql_query` 升级后**仍由 `analyst` 承载**，
> 不必为此拆角色。YAGNI —— 等真正引入 S3/OSS、元数据/血缘等**多种异构数据源**时再拆。

| 角色 | 建议 | 依据 |
|---|---|---|
| **QA/质检 Agent** | ✅ **新增** | 对应来源 A §二「需重点定制」的第 2 条：让 Agent **自动发现异常并停止**，而不是一本正经地胡说八道。这是 Harness 的**差异化能力**，不是可有可无的装饰。职责：审查幸存者偏差、辛普森悖论、数据泄露、口径不一致 |
| `coder` | ✅ **保留** | 来源 A 无形中把它并入了"分析建模"，但来源 A §1.2 自己就说数据分析的核心在**「代码执行的安全性与灵活性」** —— 把代码执行角色并掉与这个判断自相矛盾 |
| `executor` | ✅ **保留** | 它是 planner 派发**未匹配到专门角色**时的兜底（`tools=["*"]`）。去掉会让无法归类的任务**无处派发**，直接削弱编排健壮性 |
| 「数据接入」是否独立成角色 | ⚠️ **取决于 C5** | 若 C5 引入多数据库连接 + 元数据/血缘，独立"数据接入 Agent"更清晰；若仍以文件为主，现有 `inspector` 兼任即可。**故此项与 C5 联动，C5 定了再定** |

**结果**：基线 **8 个**（现状 7 + QA）；若 C5 扩多数据源则 **9 个**（+ 数据接入）。

### ⚠️ C3 · 链路追踪的目标平台与内容

| | 方案 |
|---|---|
| **来源 A** | 通过 **Kafka 发送到 Langfuse / Arize**；埋点含请求、规划、SQL、代码执行、**Token 消耗**；且**记录 AI 生成的 Python 代码以便审计和复现** |
| **来源 B（现状已实现）** | Kafka 上送**公司链路追踪平台**（`harness/trace/tracer.py` + `kafka_producer.py`），本地 JSONL 回退 |

- **分歧点**：目标平台不同；来源 A 额外要求 **Token 消耗埋点** 与 **生成代码留档**（现状均无）。
- **影响面**：`tracer` 的 span 字段、Kafka 消息 schema、Trace 存储。
- **待拍板**：目标平台（Langfuse／Arize／公司平台）；是否补 Token 与代码留档。

#### C3 建议方案（**已拍板** 2026-09-25）

> **已定**：① **保留 Kafka 管道不变**；② 接收端**做成可配置**（Langfuse 是其一个选项，**首期不部署 Langfuse 服务**，理由见 C4 遗留项）；③ **补 Token 埋点**；④ **补生成代码留档**。
>
> **生成代码留档的落盘位置**（与 C1 暂缓决定的衔接）：C1 已定维持现状目录，
> **当前没有 `/workspace/scripts`**，故留档落 **`/workspace` 根**，文件名带可辨识前缀
> `exec_<时间戳>_<工具名>.py`；等 C1 解冻、`/workspace/scripts` 建立后再迁移。
> 这样既达成"审计与复现"的目标，又不因 C1 暂缓而卡住 C3。

**先澄清一个误解**：来源 A 说的是「通过 **Kafka** 将日志发送到 **Langfuse/Arize**」——
即 **Kafka 是管道、Langfuse 是接收端**。这与现状的「Kafka → 公司平台」**是同一位置的两个接收端，不是两套架构**。

因此建议：

| 项 | 建议 | 依据 |
|---|---|---|
| 传输层 | **保留 Kafka 不变** | 与来源 A 一致；且「上送公司链路追踪平台」是参考设计的真实场景，架构上不该丢 |
| 接收端 | **做成可配置，默认自建 Langfuse** | 同一管道换接收端即可；自建 Langfuse 可演示、有 UI（补上本项目"执行链路可视化"的待办） |
| **Token 埋点** | ✅ **补** | **实测核准：`LLMClient` 当前丢弃了 `usage`**（`_raw_chat` 里无任何 usage 处理）。OpenAI SDK 的 `resp.usage` 现成可拿 —— **改动很小、价值很高**（成本可观测、可归因到子任务/子 Agent） |
| **生成代码留档** | ✅ **补** | **实测核准：沙箱当前不留档生成的代码**。建议落 **`/workspace/scripts`**（正好用上 C1 里来源 A 提出的该目录），支撑来源 A 要求的"审计与复现" |

> C1 与 C3 有协同：`/workspace/scripts` 的存在理由，正是 C3 的"生成代码留档"。两条建议互相印证。

### ⚠️ C4 · 手搓 vs 拿来主义（路线冲突，影响面最大）

来源 A §二 明确列出**应直接复用的成熟基础设施**，而现状多处是**手写**：

| 能力 | 来源 A 指定 | 现状 | 冲突 |
|---|---|---|---|
| **审批 HITL** | **LangGraph 原生支持"中断"与"审批节点"** | 未实现，原计划自研「挂起-恢复 + 审批断点」 | ⚠️ **直接决定 §7.1 那个待办该自研还是用 LangGraph interrupt** |
| 记忆 | Redis 短期 + 向量库（Milvus/**Qdrant**）；**Mem0 / Zep / LangChain Memory** 已封装"提取-写入-检索" | 手写三层记忆（`harness/memory/`），真实后端已接 | ⚠️ 是否改为接成熟框架 |
| 可观测性 | **Langfuse / Arize Phoenix / LangSmith**，支持 OpenTelemetry | 手写 tracer + Kafka 生产者 | ⚠️ 是否替换 |
| 权限 | 传统 **RBAC/ABAC（Apache Ranger、OPA）** 成熟 | 手写 `harness/pdp.py` | ⚠️ 是否引入 OPA |
| PII 脱敏 | **Presidio** / 云厂商 NLP | 无 | 新增（无冲突，见 §0.2） |
| 缓存 | **GPTCache**、SQL 指纹缓存 | 无 | 新增（无冲突） |

- **待拍板**：上述六项的**自研／引入**边界。这是**路线级决策**，决定后续是"继续写"还是"接现成"。

#### C4 建议方案（**自研边界已拍板** 2026-09-25）

> **已拍板**：**保留现有自研模块** —— `harness/pdp.py`、`harness/memory/` 三层**维持自研**，
> 不替换为 OPA / Mem0 / Zep；**审批机制采用 LangGraph `interrupt`**（不自研挂起-恢复）。
> 理由：interrupt 是**本项目已在用的编排引擎自身能力**（同源），且审批目前**没有任何自研模块可"保留"**
> —— 自研等于从零重造 LangGraph 已有的挂起-恢复 + 检查点。
>
> **遗留三项也已拍板**（2026-09-25）：
>
> | 项 | 决定 | 理由 |
> |---|---|---|
> | **可观测** | **首期不部署 Langfuse 服务**；先把 C3 的 **Token 埋点** 做掉 | ① C3 已把接收端做成可配置，Langfuse 是其**一个选项而非前置依赖**；② 多一个外部服务就多一份**生命周期管理负担** —— 沙箱服务端"没人管、被内存回收"的坑刚踩过；③ 当务之急是**数据**（Token/成本），不是 UI。等 Token 埋点落地且确实需要可视化时再引入 |
> | **PII 脱敏** | **不引入 Presidio**；改为**自研中文 PII 规则层**（正则 + 校验位：手机号段、身份证校验码），挂中间件 Hook | **假脱敏比不脱敏更危险** —— Presidio 预置识别器偏英文，中文漏识别会让系统"看起来脱敏了、实际没有"。手机号/身份证用**正则+校验位**是确定性的且准确率高；待需要更广实体（人名、地址）时再评估 NLP 服务 |
> | **缓存** | **SQL 指纹缓存自研**（Redis，确定性）；**不引入 GPTCache / 语义缓存** | 数据分析场景查询**很少"语义近似重复"**；更关键的是语义缓存有**命中错误结果**的风险 —— 对数据分析是致命的（**口径必须精确**，不能被"相似"糊过去） |

判断不按"哪个更成熟"，而按三条**稳健性条件**：

> ① **抽象是否匹配需求** —— 不匹配时成熟框架反而是负担（要塞、要绕、要 fork）
> ② **是否与已有栈同源** —— 同源 = 白捡；异构 = 要算运维账（多一个要懂、要升级、要排障的东西）
> ③ **是否能够评估它** —— 评估不了不叫稳健，叫赌

外加本项目特有的一条约束：

> ④ **换掉它会不会把项目换没了** —— 本项目的定位是**手写 Harness 管控层**；
> 把 memory / tracer / PDP 全换成现成框架，定位就从"自研管控层"退化为
> "拼装 LangGraph + 几个现成服务"。这与当初拒绝"整个替换沙箱"是同一条理由
> —— 那次的做法是**把 OpenSandbox 作为运行时后端插进来**，而非替换整个模块。

| 项 | 建议 | 依据 |
|---|---|---|
| **审批 HITL** | ✅ **必用现成**：LangGraph `interrupt` / 审批节点 | **条件②同源** —— LangGraph 已是我们的编排引擎，interrupt 是其内建能力，与 checkpointer 天然配套。自研挂起-恢复 = **重造已有东西**，还要自己处理状态序列化、恢复点、并发。且条件④不冲突（本就属编排引擎能力，非 Harness 管控层卖点）。**顺带把闲置的 checkpointer 用起来** |
| 记忆 · 短期 | **保留自研** | 就是简单 KV（对话历史/断点），引框架是杀鸡用牛刀 |
| 记忆 · 长期 | **取决于需求**：是否要"自动抽取" | 现状"存进去 + 相似度查"已工作。若要做来源 A 的"经验沉淀 / 自我进化"，Mem0/Zep 那类 **LLM 驱动自动抽取**确有优势 —— **这是需求问题，非技术问题**。注意条件④：换掉会动摇定位 |
| **可观测** | ✅ 倾向**引入 Langfuse** | 自研要重造三样：span schema、**可视化 UI**（本项目"执行链路 UI"仍在待办）、Token/成本统计；且来源 A 要求的"记录生成的 Python 代码以便复现"其原生支持。条件④影响小（链路追踪本就是"接现成平台"性质） |
| 权限 · **工具级** | **保留自研 PDP** | 三级 RBAC 简单够用；OPA 的价值（Rego + 策略集中分发）在单服务场景用不上。条件④：**PDP 是点名的自研管控点，换掉即动摇定位** |
| 权限 · **行列级** | ⚠️ **单独设计**，不是引入 OPA 就算完 | "强制注入 `WHERE`" 是**数据层**问题（查询改写 / 视图 / 行级安全）；OPA 只管"准不准"，管不了"改 SQL"。属 §0.2 新增能力 |
| **PII 脱敏** | 倾向引入，但**必须先验证中文效果** | Presidio 预置识别器偏英文，中文身份证/手机号场景**不能盲信**，须实测后再决定（条件③） |
| 缓存 | **SQL 指纹缓存自研**（确定性，几十行）；语义缓存按需 | 来源 A 提的 SQL 指纹是**确定性**的（SQL 文本哈希），GPTCache 是**语义**缓存，两者解决的不是同一个问题 |

**归纳**：真正"必用现成"的只有 **审批**（同源，自研即重造）与 **可观测**（UI 重造成本高）；
**PDP 与记忆三层应保留自研**（它们是 Harness 管控层的卖点）；
**行列级权限、数据质量拦截、口径治理**属新能力，与自研/现成之争无关，需单独设计；
**PII 先做中文可行性验证**再谈引入。

### ⚠️ C5 · 数据源范围

| | 范围 |
|---|---|
| **来源 A** | 数据库（**MySQL、PostgreSQL、ClickHouse、Hive**，支持分页、超时、强制 Limit 防 OOM）、文件（CSV/Excel/Parquet/JSON，对接 **S3/OSS**）、元数据（表结构、字段注释、数据量级、**数据血缘**）、API（企业内部系统、第三方 SaaS） |
| **来源 B（现状已实现）** | `sql_query` **仅支持 SQLite 只读**（SELECT/WITH 白名单、强制 LIMIT、mode=ro） |

- **影响面**：`tools/sql_query.py` 需重写为多数据源；新增连接管理、驱动依赖、权限模型。
- **待拍板**：优先支持哪几种数据源；是否引入统一连接层（如 SQLAlchemy）。

#### C5 建议方案（**已拍板** 2026-09-25）

> **已定范围**：首期 = **SQLAlchemy 统一连接层 + MySQL / PostgreSQL**（保留 SQLite），现有只读安全约束全部保留；其余（ClickHouse / Hive / S3·OSS / 元数据血缘 / 通用 API）留第二步。
>
> **已定排序：C5 排在服务化 / ContextManager 接线 / Skills / 审批之后。**
> 理由：§4.3 的阻塞分析里，**多数据源不是阻塞项** —— 现有 SQLite 路径足以支撑端到端链路；
> 而服务化、上下文管理、Skills、审批是。先做阻塞项，不因"来源 A 提了"就抢跑。

**先说清性质**：这是 §零 里**工作量最大**的一项。来源 A 列的是**目标形态**，不是首期范围 —— 一次全上既不现实，也会把战线拉垮。建议分批。

**第一步（首期）**：引入 **SQLAlchemy 统一连接层**，支持 **MySQL / PostgreSQL**，保留 SQLite，把 `tools/sql_query.py` 从「仅 SQLite 只读」升级为「**多数据源只读**」。

理由：**SQLAlchemy 一次解决多库**。不引入它，每加一个数据库都要重写驱动、方言、分页、连接管理 —— 成本是线性的；引入后是第一家成本高、后续接近零。

**保留现有安全约束不变**（这是已有资产，不该丢）：SELECT/WITH 白名单、禁多语句、强制 LIMIT、参数化、超时、只读账号/只读连接。

**第二步（后续，按需）**：

| 数据源 | 排序理由 |
|---|---|
| ClickHouse / Hive | 数仓场景价值高，但**本地难搭、驱动重**，成本高于前三者 |
| S3 / OSS 对象存储 | boto3 / oss2 成熟，中等成本 |

**不建议首期即做**：Hive（需 Hadoop 环境）、元数据血缘（依赖企业侧）、通用 API（无边界）。

# 一、项目定位与设计哲学

## 1.1 是什么

**通用工业级 Agent Harness Engineering 框架库**，当前以**数据分析**为首个领域实例。
LangGraph 负责编排，手写 Harness 管控层负责工具/权限/记忆/追踪/沙箱/质量门等企业能力。

来源 A 给出的最终产品形态愿景：

> 具备**企业上下文感知、代码执行能力、自我纠错机制和安全合规边界**的
> **「虚拟高级数据分析师」**。可根据场景演化为：对话式分析助手（ChatBI）、数据分析
> Copilot、自动化报告机器人（定时 Workflow）以及企业级 Agent 编排平台（PaaS）。

## 1.2 与风控策略 Agent 的差异（来源 A 的核心判断）

> 相比风控策略 Agent，数据分析 Agent 的核心在于
> **「代码执行的安全性与灵活性」**、**「大数据量下的上下文管理」**、
> **「业务口径的统一与合规」**。

这三点直接对应本项目当前的三个薄弱处：沙箱（已解决）、ContextManager 接线（未做）、口径治理（未做）。

## 1.3 设计哲学（沿用来源 B，仍然有效）

- **框架只做管控，业务由你注入**：换不同工具 = 不同应用。
- **确定性优先，LLM 只做推理**：状态管理/工具执行/权限判断/审计/文件操作是确定性代码；关键路径上凡有 LLM 处都有确定性兜底。
- **管控点横切，不侵入业务**：PDP/审计/限流/PII/缓存/重试经中间件 Hook 注入，业务工具不需要知道管控逻辑存在。
- **大结果沉淀，小上下文推理**：大结果落 VFS，模型上下文只保留摘要 + 文件链接 + 下一步计划。
- **可观测性内建**：不是出了问题再加日志，而是设计时就把链路追踪做进去。

## 1.4 智能体执行范式（已拍板，勿反复）

**顶层 Plan-and-Execute + 每个子任务内 ReAct**：

- **顶层 = Plan-and-Execute**：Planner 把目标拆成有序、带依赖的 `TaskPlan`；Dispatch 逐个取出子任务；交给执行体；全部完成后 Synthesize；偏离/失败时 Replan。
- **执行体 = ReAct 内核**：单个子任务内部 think→action→observation 循环，见机行事。

一句话：**宏观用 Plan 保证方向与覆盖（确定性骨架），微观用 ReAct 应对每步不确定性（探索性执行）。**

来源 A 对此的表述一致：「将复杂的数据分析需求拆解为 DAG（有向无环图）」，主 Agent 拆解为
`数据获取 → 清洗 → 探索性分析 → 深度建模 → 可视化 → 报告生成`。

| **报告与图表** | 图表选择 SOP（防止乱画图）；报告排版 SOP（摘要→核心指标→归因→结论与建议）；PPT 生成 Skill（自动填充企业标准 PPT 模板） |
| **自我进化** | 根据历史任务复盘，将成功的分析路径、纠正过的 SQL 错误、优秀的可视化代码**沉淀为新 Skill** |

> **现状**：❌ **完全没有实现**。`harness/skills/` 是空目录。
> 但数据模型已预留：`SubAgentDef` 有 `skills` 字段（`harness/agents/registry.py`），只是无人使用。

# 六、既有架构决策（已拍板，勿反复）

| # | 决策 | 说明 |
|---|---|---|
| D1 | **执行范式** | 顶层 Plan-and-Execute + 子任务内 ReAct（§1.4） |
| D2 | **质量门五处置** | PASS / RETRY / REPLAN / HUMAN / FAIL；Critic 仅在 `use_critic` 且有验收标准时调用，故障时 fail-open 保留硬校验 |
| D3 | **工具与协议解耦** | 一份工具可被 ReAct / FC / MCP 复用，归一 `broker.invoke` |
| D4 | **FC 与 MCP 分层** | ReAct/FC 属模型决策层（二选一、可切换）；MCP 属工具接入/传输层，不冲突 |
| D5 | **沙箱用 OpenSandbox，不手写 Docker 隔离** | 服务端锁 **0.2.3**（1.1.0 的 wheel 缺 protobuf 包，启动即崩）；服务端用**独立 venv**（依赖重，勿与项目 `.venv` 合并） |
| D6 | **双层文件访问平面** | 主机 VFS ↔ 沙箱私有 FS，经 SDK Filesystem API 显式搬运，**禁止 bind mount**（`allowed_host_paths=[]`） |
| D7 | **沙箱失败 fail closed** | 宿主上**不存在**进程级回退路径 |
| D8 | **保留 egress sidecar** | 它是 FQDN 级出网管控 + 凭证保险箱的承载点，属企业级必要能力；**不得以"当前用不到"为由裁剪** |
| D9 | **`tool_mode` 是框架级配置** | 环境变量 `AGENT_TOOL_MODE`，非示例私有开关 |
| D10 | **FC 批量 tool_calls 按序执行** | 不真并行 —— 限流是工具维度滑动窗口、审计要保序、沙箱有并发上限 |
| D11 | **MCP 接入不绕过管控** | Server 方向暴露的工具仍经 `broker.invoke`，PDP/校验/限流/沙箱/审计同样生效 |
| D12 | **绝对导入** | 新模块统一 `from harness.xxx` / `from tools.xxx` |
| D13 | **内置工具保持通用** | 不写 IV/WOE/KS/PSI 等风控专有指标 |
| D14 | **上下文管理保持内联**（不改为独立图节点） | 独立节点的唯一实质收益是**拓扑可见性**，代价是**状态字段进检查点**（长任务持续成本）+ 改拓扑 + 自纠路径边界易漏。而"可独立测试"这一收益**已具备**（压缩逻辑有 12 项独立测试）。**用持续的状态成本换一次性的可见性，不划算** |
| D15 | **上下文压缩采用边界约束机制**（`start_on` / `end_on`），默认值取本协议安全值 | 与主流框架同名同义（其为 `pre_model_hook` / `trim_messages` 的边界约束），但**默认值更严**：禁止保留窗口以"工具结果"类消息开头。理由：本方法服务本项目协议，该协议要求工具调用与其结果成对，**默认 None 会让调用方忘记设置而引入只在长任务暴露的间歇 400**。需要时可显式传 None 关闭 |
| D16 | **装配点模式**：框架提供参数并贯通，**应用层构造实例并注入** | 既非隐式全局（不偷偷 new），也不要求每个调用方各记一遍。当前装配点＝示例程序；阶段5 后＝服务层 |
| D17 | **配置化优先**：预算 / 阈值类参数一律进配置段，不留代码内硬编码 | 本轮把上下文预算的 5 个硬编码值配置化（原先 6 项只有 1 项来自配置）。理由：这类值直接改变行为、需按环境与模型窗口调整，且散落硬编码会造成"改不动也说不清" |

# 附录 A：现有六个工具的详细设计（保留自来源 B）

> 六个工具均已实现并通过冒烟。统一契约：**一个 `ToolDef`（说明书，`parameters` 为标准 JSON Schema）
> + 一个 `handler(args, context) -> (ok: bool, text: str, artifacts: dict)`**。
> 工具内部**不出现任何 ReAct / Function Calling / MCP / OpenAI 字样** —— 调用协议由上层 nodes 决定，
> 因此一份工具可同时被三种范式复用。产物统一落 VFS：清洗后数据进 `/workspace`，报告与图表进 `/reports`。

**主链路**：
```
data_inspector → data_cleaner → eda → chart_generator → code_executor
 （体检/认识数据）  （清洗/产出净集） （统计/找规律） （可视化发现）  （兜底/自定义深挖）
                                                        ▲
sql_query（数据库场景）：数据源是 DB 而非文件时，替代前 3 步的文件读取路径
```

| 工具 | 定位 | 管控属性 |
|---|---|---|
| `data_inspector` | 文件层/结构层/Schema 层/样例层探查 + 风险标记（全空列、常量列、高缺失、疑似主键/目标/时间列） | analyst · 30/min · 只读 |
| `data_cleaner` | 缺失/重复/类型修正/异常值（IQR·Z-score）/文本规范/列处理；产出干净集 + 清洗报告 | analyst · 20/min |
| `eda` | 单变量（数值/类别/时间）、双变量（Pearson/Spearman/ANOVA/卡方）、目标关系、异常检测、业务汇总 | analyst · 15/min · 只读 |
| `sql_query` | **仅 SQLite 只读**（⚠️ C5 待扩）：SELECT/WITH 白名单、禁多语句、`mode=ro`+`query_only`、强制 LIMIT、参数化、超时 | analyst · 30/min · 只读 |
| `chart_generator` | bar/line/scatter/hist/pie/box/heatmap + auto 选型、中文字体探测、PNG 落 `/reports/charts` | analyst · 20/min |
| `code_executor` | **在 OpenSandbox 隔离容器中执行**（无网络/资源限额/超时强杀）；双层文件平面往返；无宿主回退路径。⚠️ `requires_approval=True` 但**审批闸门未实现** | senior_analyst · 5/min · 需审批 |
