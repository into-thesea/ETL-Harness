#### C4 建议方案（**待确认，未拍板**）

判断不按"哪个更成熟"，而按三条**稳健性条件**：

> ① **抽象是否匹配需求** —— 不匹配时成熟框架反而是负担（要塞、要绕、要 fork）
> ② **是否与已有栈同源** —— 同源 = 白捡；异构 = 要算运维账（多一个要懂、要升级、要排障的东西）
> ③ **是否能够评估它** —— 评估不了不叫稳健，叫赌

外加本项目特有的一条约束：

> ④ **换掉它会不会把项目换没了** —— 本项目的定位是**手写 Harness 管控层**；
> 把 memory / tracer / PDP 全换成现成框架，定位就从"自研管控层"退化为
> "拼装 LangGraph + 几个现成服务"。这与当初拒绝"整个替换沙箱"是同一条理由
> —— 那次的做法是**把 OpenSandbox 作为运行时后端插进来**，而非替换整个模块。

| 项 | 建议 | 依据 |
|---|---|---|
| **审批 HITL** | ✅ **必用现成**：LangGraph `interrupt` / 审批节点 | **条件②同源** —— LangGraph 已是我们的编排引擎，interrupt 是其内建能力，与 checkpointer 天然配套。自研挂起-恢复 = **重造已有东西**，还要自己处理状态序列化、恢复点、并发。且条件④不冲突（本就属编排引擎能力，非 Harness 管控层卖点）。**顺带把闲置的 checkpointer 用起来** |
| 记忆 · 短期 | **保留自研** | 就是简单 KV（对话历史/断点），引框架是杀鸡用牛刀 |
| 记忆 · 长期 | **取决于需求**：是否要"自动抽取" | 现状"存进去 + 相似度查"已工作。若要做来源 A 的"经验沉淀 / 自我进化"，Mem0/Zep 那类 **LLM 驱动自动抽取**确有优势 —— **这是需求问题，非技术问题**。注意条件④：换掉会动摇定位 |
| **可观测** | ✅ 倾向**引入 Langfuse** | 自研要重造三样：span schema、**可视化 UI**（本项目"执行链路 UI"仍在待办）、Token/成本统计；且来源 A 要求的"记录生成的 Python 代码以便复现"其原生支持。条件④影响小（链路追踪本就是"接现成平台"性质） |
| 权限 · **工具级** | **保留自研 PDP** | 三级 RBAC 简单够用；OPA 的价值（Rego + 策略集中分发）在单服务场景用不上。条件④：**PDP 是点名的自研管控点，换掉即动摇定位** |
| 权限 · **行列级** | ⚠️ **单独设计**，不是引入 OPA 就算完 | "强制注入 `WHERE`" 是**数据层**问题（查询改写 / 视图 / 行级安全）；OPA 只管"准不准"，管不了"改 SQL"。属 §0.2 新增能力 |
| **PII 脱敏** | 倾向引入，但**必须先验证中文效果** | Presidio 预置识别器偏英文，中文身份证/手机号场景**不能盲信**，须实测后再决定（条件③） |
| 缓存 | **SQL 指纹缓存自研**（确定性，几十行）；语义缓存按需 | 来源 A 提的 SQL 指纹是**确定性**的（SQL 文本哈希），GPTCache 是**语义**缓存，两者解决的不是同一个问题 |

**归纳**：真正"必用现成"的只有 **审批**（同源，自研即重造）与 **可观测**（UI 重造成本高）；
**PDP 与记忆三层应保留自研**（它们是 Harness 管控层的卖点）；
**行列级权限、数据质量拦截、口径治理**属新能力，与自研/现成之争无关，需单独设计；
**PII 先做中文可行性验证**再谈引入。

# 一、项目定位与设计哲学

## 1.1 是什么

**通用工业级 Agent Harness Engineering 框架库**，当前以**数据分析**为首个领域实例。
LangGraph 负责编排，手写 Harness 管控层负责工具/权限/记忆/追踪/沙箱/质量门等企业能力。

来源 A 给出的最终产品形态愿景：

> 具备**企业上下文感知、代码执行能力、自我纠错机制和安全合规边界**的
> **「虚拟高级数据分析师」**。可根据场景演化为：对话式分析助手（ChatBI）、数据分析
> Copilot、自动化报告机器人（定时 Workflow）以及企业级 Agent 编排平台（PaaS）。

## 1.2 与风控策略 Agent 的差异（来源 A 的核心判断）

> 相比风控策略 Agent，数据分析 Agent 的核心在于
> **「代码执行的安全性与灵活性」**、**「大数据量下的上下文管理」**、
> **「业务口径的统一与合规」**。

这三点直接对应本项目当前的三个薄弱处：沙箱（已解决）、ContextManager 接线（未做）、口径治理（未做）。

## 1.3 设计哲学（沿用来源 B，仍然有效）

- **框架只做管控，业务由你注入**：换不同工具 = 不同应用。
- **确定性优先，LLM 只做推理**：状态管理/工具执行/权限判断/审计/文件操作是确定性代码；关键路径上凡有 LLM 处都有确定性兜底。
- **管控点横切，不侵入业务**：PDP/审计/限流/PII/缓存/重试经中间件 Hook 注入，业务工具不需要知道管控逻辑存在。
- **大结果沉淀，小上下文推理**：大结果落 VFS，模型上下文只保留摘要 + 文件链接 + 下一步计划。
- **可观测性内建**：不是出了问题再加日志，而是设计时就把链路追踪做进去。

## 1.4 智能体执行范式（已拍板，勿反复）

**顶层 Plan-and-Execute + 每个子任务内 ReAct**：

- **顶层 = Plan-and-Execute**：Planner 把目标拆成有序、带依赖的 `TaskPlan`；Dispatch 逐个取出子任务；交给执行体；全部完成后 Synthesize；偏离/失败时 Replan。
- **执行体 = ReAct 内核**：单个子任务内部 think→action→observation 循环，见机行事。

一句话：**宏观用 Plan 保证方向与覆盖（确定性骨架），微观用 ReAct 应对每步不确定性（探索性执行）。**

来源 A 对此的表述一致：「将复杂的数据分析需求拆解为 DAG（有向无环图）」，主 Agent 拆解为
`数据获取 → 清洗 → 探索性分析 → 深度建模 → 可视化 → 报告生成`。

## 2.1 工具层（Tool Layer）

工具层是 Agent 的"手脚"。来源 A 划分为五类：

### 2.1.1 数据接入与探查工具
- 数据库查询：MySQL、PostgreSQL、ClickHouse、Hive 等，**支持分页、超时控制、强制 Limit 防 OOM** ⚠️ C5（现仅 SQLite）
- 文件读取：CSV、Excel、Parquet、JSON；对接 S3/OSS ⚠️ C5
- 元数据获取：表结构、字段注释、数据量级、数据血缘 ⚠️ 新增
- API 调用：企业内部业务系统、第三方 SaaS 数据 API ⚠️ 新增

### 2.1.2 数据处理与执行工具（核心沙箱）
- **Python 执行器**（Pandas/Polars/NumPy）：复杂数据清洗与特征工程
- **SQL 执行器**：将计算下推至数据库
- R 执行器 ⚠️ 新增
- **安全机制**（来源 A 明确）：所有代码执行必须运行在隔离沙箱中（**如 OpenSandBox 或 Docker**），限制网络访问和本地文件系统挂载，只允许读取特定的数据挂载目录

> **现状**：✅ 已实现且符合该要求 —— `tools/code_executor.py` 经 **OpenSandbox** 隔离容器执行，
> 网络默认 deny、双层文件访问平面、无 bind mount、fail closed。见 §六 D5。

### 2.1.3 分析与建模工具
- 统计检验工具（T 检验、卡方检验等）

### 2.1.4 可视化与报告产出工具

## 2.2 Skill 层（技能系统）

> Skill 层是 Agent 的"专业知识"，解决**如何正确使用工具**。按渐进式披露原则，
> Skill 应包含 SOP、Prompt、SQL 模板、领域文档和 Python 脚本。

| 类别 | Skill |
|---|---|
| **数据清洗** | 数据探查 SOP（缺失率、唯一值、异常值、分布）；缺失值处理（均值/中位数/众数填充、插值、剔除）；异常值处理（Z-score、IQR、分位数截断/盖帽法）；数据标准化（Z-Score、Min-Max）；**口径统一（结合长期记忆，将业务黑话转换为标准 SQL 逻辑）** |
| **数据分析** | 描述性统计（均值、方差、同环比、多维交叉表）；归因分析（漏斗分析、杜邦分析）；时间序列（趋势、季节性、异常波动检测）；**A/B 实验分析**（假设检验、置信区间、显著性判定） |
| **报告与图表** | 图表选择 SOP（防止乱画图）；报告排版 SOP（摘要→核心指标→归因→结论与建议）；PPT 生成 Skill（自动填充企业标准 PPT 模板） |
| **自我进化** | 根据历史任务复盘，将成功的分析路径、纠正过的 SQL 错误、优秀的可视化代码**沉淀为新 Skill** |

> **现状**：❌ **完全没有实现**。`harness/skills/` 是空目录。
> 但数据模型已预留：`SubAgentDef` 有 `skills` 字段（`harness/agents/registry.py`），只是无人使用。

## 2.3 Agent 编排与上下文管理

> **现状**：✅ 已实现。`harness/orchestrator.py` 的 Plan-and-Execute 主图，
> 含 plan / dispatch / execute / gate / replan / human / synthesize 节点，
> 质量门五处置（PASS/RETRY/REPLAN/HUMAN/FAIL）、ScopedBroker 最小授权。

### 2.3.2 专职子 Agent（减少上下文污染）

`/workspace/charts`、`/reports/final`。**⚠️ 与现状目录方案的差异见 §0.1 C1。**

**关键点（来源 A 原话）**：
> 大工具结果**绝不进入模型上下文**，只写入 VFS，上下文中只保留**路径、形状、字段列表和摘要**。

> **现状**：⚠️ **模块已实现但未接线** —— `harness/context/manager.py` 的 ContextManager

| D3 | **工具与协议解耦** | 一份工具可被 ReAct / FC / MCP 复用，归一 `broker.invoke` |
| D4 | **FC 与 MCP 分层** | ReAct/FC 属模型决策层（二选一、可切换）；MCP 属工具接入/传输层，不冲突 |
| D5 | **沙箱用 OpenSandbox，不手写 Docker 隔离** | 服务端锁 **0.2.3**（1.1.0 的 wheel 缺 protobuf 包，启动即崩）；服务端用**独立 venv**（依赖重，勿与项目 `.venv` 合并） |
| D6 | **双层文件访问平面** | 主机 VFS ↔ 沙箱私有 FS，经 SDK Filesystem API 显式搬运，**禁止 bind mount**（`allowed_host_paths=[]`） |
| D7 | **沙箱失败 fail closed** | 宿主上**不存在**进程级回退路径 |
| D8 | **保留 egress sidecar** | 它是 FQDN 级出网管控 + 凭证保险箱的承载点，属企业级必要能力；**不得以"当前用不到"为由裁剪** |
| D9 | **`tool_mode` 是框架级配置** | 环境变量 `AGENT_TOOL_MODE`，非示例私有开关 |
| D10 | **FC 批量 tool_calls 按序执行** | 不真并行 —— 限流是工具维度滑动窗口、审计要保序、沙箱有并发上限 |
| D11 | **MCP 接入不绕过管控** | Server 方向暴露的工具仍经 `broker.invoke`，PDP/校验/限流/沙箱/审计同样生效 |
| D12 | **绝对导入** | 新模块统一 `from harness.xxx` / `from tools.xxx` |
| D13 | **内置工具保持通用** | 不写 IV/WOE/KS/PSI 等风控专有指标 |

# 附录 A：现有六个工具的详细设计（保留自来源 B）

> 六个工具均已实现并通过冒烟。统一契约：**一个 `ToolDef`（说明书，`parameters` 为标准 JSON Schema）
> + 一个 `handler(args, context) -> (ok: bool, text: str, artifacts: dict)`**。
> 工具内部**不出现任何 ReAct / Function Calling / MCP / OpenAI 字样** —— 调用协议由上层 nodes 决定，
> 因此一份工具可同时被三种范式复用。产物统一落 VFS：清洗后数据进 `/workspace`，报告与图表进 `/reports`。

**主链路**：
```
data_inspector → data_cleaner → eda → chart_generator → code_executor
 （体检/认识数据）  （清洗/产出净集） （统计/找规律） （可视化发现）  （兜底/自定义深挖）
                                                        ▲
sql_query（数据库场景）：数据源是 DB 而非文件时，替代前 3 步的文件读取路径
```

| 工具 | 定位 | 管控属性 |
|---|---|---|
| `data_inspector` | 文件层/结构层/Schema 层/样例层探查 + 风险标记（全空列、常量列、高缺失、疑似主键/目标/时间列） | analyst · 30/min · 只读 |
| `data_cleaner` | 缺失/重复/类型修正/异常值（IQR·Z-score）/文本规范/列处理；产出干净集 + 清洗报告 | analyst · 20/min |
| `eda` | 单变量（数值/类别/时间）、双变量（Pearson/Spearman/ANOVA/卡方）、目标关系、异常检测、业务汇总 | analyst · 15/min · 只读 |
| `sql_query` | **仅 SQLite 只读**（⚠️ C5 待扩）：SELECT/WITH 白名单、禁多语句、`mode=ro`+`query_only`、强制 LIMIT、参数化、超时 | analyst · 30/min · 只读 |
| `chart_generator` | bar/line/scatter/hist/pie/box/heatmap + auto 选型、中文字体探测、PNG 落 `/reports/charts` | analyst · 20/min |
| `code_executor` | **在 OpenSandbox 隔离容器中执行**（无网络/资源限额/超时强杀）；双层文件平面往返；无宿主回退路径。⚠️ `requires_approval=True` 但**审批闸门未实现** | senior_analyst · 5/min · 需审批 |
