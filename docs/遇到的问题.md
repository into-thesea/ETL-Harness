# 遇到过的问题

> 记录开发过程中**真跑才暴露**的问题与最终解法。都是实测撞出来的，不是推演出来的。
> 目的是让别人（也包括未来的自己）不必重踩。
>
> 分两类：**一、代码缺陷**（改了代码解决）；**二、文档与决策偏差**（改了计划或认知解决）。

---

## 一、代码缺陷

### 1. 配置文件整体失效，框架一直跑默认值

**现象**：改配置文件不生效，模型名、密钥、各服务地址始终是代码里的默认值。而且**不报错**，看上去一切正常。

**根因**：配置框架的"从文件加载环境变量"机制**不会向下传播到嵌套的配置模型**。顶层配置虽然声明了配置文件，但每个子配置（模型、缓存、消息队列、对象存储、沙箱、记忆……）各自是独立模型，只从进程环境读，于是配置文件对它们形同不存在。等于**整个配置体系一直是摆设**。

**解法**：在实例化任何配置之前，显式把配置文件载入进程环境（锚定绝对路径，不依赖当前工作目录），使所有层级都能读到。

**影响面**：这一处修复让**全部配置段**同时生效，不只是模型。此前所有"降级为本地实现"的判断，有一部分其实是配置没读到造成的假象。

---

### 2. 沙箱隔离能力：官方发布的服务端**装不起来**

**现象**：按官方文档安装的沙箱服务端，启动即崩，报缺一个自动生成的协议模块。

**根因**：官方打进包里的服务端**漏打了该协议模块**，属上游打包缺陷；该版本不可用。

**解法**：服务端**锁定到未受影响的旧版本**（客户端仍用新版，二者协议兼容）。同时把服务端装进**独立环境**，不与项目主环境混装 —— 它的依赖又重又杂，混装会污染主环境。

**附带影响**：这个服务端是**独立基础设施**，有它自己的生命周期问题（见第三类）。

---

### 3. 命令提交格式与服务端不匹配

**现象**：沙箱建起来了，但提交执行命令时被服务端以"命令字段缺失"拒绝。

**根因**：客户端 SDK 允许传"参数数组"形式的命令，但服务端的校验只接受**字符串**形式。新版特性与旧版服务端不一致。

**解法**：按服务端要求改传字符串。

---

### 4. 沙箱里没有可写目录

**现象**：隔离执行成功，但代码写产物时报"目录不存在"。

**根因**：沙箱镜像本身不含工作用的输入/输出目录。

**解法**：**用文件系统接口在运行时创建目录**，而不是依赖镜像预置 —— 这样换任何镜像都成立，不绑定到某个镜像的构建方式。

---

### 5. 超时被误判为普通失败

**现象**：超时确实触发了（进程被杀），但系统把它归类成"执行失败"而非"超时"，导致上层无法区分。

**根因**：判定逻辑依赖执行完成事件里的耗时字段，而**被强制杀掉的进程根本没有完成事件**，字段为空。

**解法**：改为**量测提交命令到返回的实际耗时窗口**，与设定上限比对。不再依赖那个不存在的字段。

---

### 6. 原生工具调用被服务端以 422 拒绝

**现象**：切换到原生工具调用模式后，多轮对话到某一步突然被服务端拒绝，提示消息格式里有个"未知的变体"。

**根因**：编排框架在内部把消息**转换成了它自己的形态**，其工具调用条目用的是框架内的叫法（`type` 是框架的值、参数是字典）；而模型服务商的契约要求另一种形态（`type` 固定值、参数是 **JSON 字符串**）。原样回传必然被拒。

**解法**：在组装请求前**统一归一化**工具调用条目，并把必需的配对标识一并带过（否则多轮无法配对）。

---

### 7. MCP 工具接入：两处字段名不一致，导致**静默错误**

**现象 A**：从外部 MCP 服务拉回的工具，参数说明是**空的** —— 模型看不到该工具要什么参数。

**现象 B**：外部工具调用**失败了却被当成成功**（权限拒绝的信息被当作正常返回，上层判定成功）。

**根因**：同一件事 —— 客户端侧模型的字段命名是**下划线风格**，而代码按键名风格去取，取不到就用了兜底值。于是：参数说明退化成空；失败标志恒为"否"。

**解法**：**两种命名都取**。这类问题的危险在于**不报错**，只是行为悄悄地错。

---

### 8. MCP 工具失败被当成成功（机制层面）

**现象**：把上述字段名修好后，失败仍被当成功。

**根因**：MCP 协议把**正常返回**一律视为成功结果。我们的工具失败时只返回了一段错误文字，对协议而言那就是一次"成功的调用"。

**解法**：失败必须走**异常通道**（协议约定：预期内的失败抛特定异常，其文本会原样传给调用方；其它异常按崩溃处理，不出细节）。改后失败才被正确识别。

---

### 9. 工具认不出"虚拟路径"

**现象**：模型反复对**不存在的文件**调用工具（自己编出文件名），每次浪费一步，最终撞上步数上限，整个任务失败。

**根因（两层）**：
① 上游工具产出里给模型的是**虚拟路径**，而下游工具只接受**宿主路径**。虚拟路径在 Windows 上被判成"绝对路径"，于是直接报错，**连候选目录都不会尝试**。
② 报错只说"文件不存在"，**不告诉模型有哪些文件可用**，模型只能继续猜。

**解法**：① 先把虚拟路径**映射**成宿主路径再解析；② 报错时**列出当前可用的文件**，让模型一步自纠。

**效果（实测）**：同一目标下，任务从 `计划 v3 / 进度 55% / 状态 failed` 变为 `计划 v1 / 进度 100% / 状态 finished`。

---

### 10. 演示脚本谎报产物

**现象**：演示输出的"本次产物清单"看着正常，实际磁盘上多了好几个文件没被列出。

**根因**：清单用**写死的文件名前缀**做过滤 —— 那是给早期固定文件名的演示写的。换成真实模型后，模型自己给文件起名，全被过滤掉了。

**解法**：改为**运行前后快照对比**，列出真正新增的文件。

---

### 11. 文件大小显示成 0 KB

**现象**：一份内容完整的报告，清单里显示 `0 KB`，看起来像文件损坏。

**根因**：显示用整数除法换算，不足 1KB 的一律截断成 0。

**解法**：改为人类可读的换算（不足 1KB 显示字节）。

---

### 12. 上下文压缩会**切断工具调用配对**（长任务才发作）

**现象**：原生工具调用模式下，历史较长时**间歇性**被服务端以 400 拒绝。

**根因**：上下文压缩逻辑**写在原生工具调用出现之前**，它把消息当成"角色 + 文本"处理，**不知道工具调用与其结果必须成对存在**。它有两处会切断配对：
- 折叠边界可能正好切在"发起调用的助手消息"与"对应结果"之间；
- 预算裁剪是**逐条**判断丢弃的，会丢了发起方却留下结果。

**危险性**：只在**历史够长**时才触发 —— 短测试永远测不出，真实长任务必炸。

**解法**：引入**窗口边界约束**（与主流框架同名同义的机制），把保留窗口的起止对齐到合法角色，**永不切在配对中间**。被挤出窗口的靠前消息并入摘要而非直接丢弃，不丢信息。

**注**：此解法**不是自创** —— 主流实践的指南里明确写着"从切分点往回走，找到干净的边界"，属公认做法。

---

### 13. 上下文管理写完了却没接上（本次修复的主项）

**现象**：上下文管理模块本体完成、单测全过，但**主链路上完全不生效** —— 大结果照样灌进上下文。

**根因**：模块写完了，但没有接入执行内核的两个时机，也没往上层透传。**"有模块"和"生效"是两件事。**

**解法**：在决策前的历史组装、与工具执行后的结果处理两处接入，并逐层透传到编排层；两种工具调用模式**都接**，不留残缺。

**附带发现**：阈值参数原先**六个里只有一个来自配置**，其余五个是硬编码值 —— 已全部配置化（数值保持不变，行为不变）。

### 21. PostgreSQL 的"连接级只读"在 psycopg3 下是假的（安全措施静默失效）

**现象**：`harness/datasources/manager.py` 声明对 PG 只读源做连接级保护（`SET default_transaction_read_only=on`），但用**有写权限的账号**实测：通过框架创建的 engine 执行 `CREATE TABLE` **成功了**。保护形同虚设，且不报任何错。

**根因**：原来把 `SET` 放在 SQLAlchemy 的 `connect` 事件里执行。psycopg3 下这条 `SET` 会隐式开启一个事务，连接归还连接池时的 `rollback` 把设置**一并回滚** —— 会话实际是可写的。

**解法**：改用连接参数在建立会话时下发 —— PG `connect_args={"options": "-c default_transaction_read_only=on"}`；MySQL 同理 `connect_args={"init_command": "SET SESSION TRANSACTION READ ONLY"}`（MySQL 没有 PG 那种连接参数）。

**为什么之前一直没暴露**：只读账号那条路上，数据库在**权限层**就先拒绝了写操作，连接级开关从未被真正检验。是用"**管理员账号 + 写入必须失败**"这条用例把它单独逼出来的。

**判据**：安全措施必须用"绕过它之外所有防线"的方式验证 —— 否则你验证的是别的防线，而不是这一条。

### 22. 三个管控点"有模块≠生效"（同一类问题的第三次）

- **PII 中间件**：`PIIDetectionMiddleware` 存在已久，但**全项目没有任何地方注册它**（装配点既不传 middleware_manager，也不传 middleware）→ 脱敏完全空转。而且脱敏方向不全：只脱敏工具返回的**文本**（真实行数据在 artifacts 里）、**完全不脱敏发给模型的提示词**。
- **PDP**：`ToolBroker(pdp=...)` 在生产装配里从没传过 → `invoke` 里 `if self.pdp is not None` 恒假，工具级鉴权从未生效。
- **`ToolDef.required_role`**：从未被强制执行，只在注册时记一行日志。

**解法**：三者都接上（中间件同时挂 broker 与图的 middleware —— LLM 钩子走图、工具钩子走 broker，两条通路都要；PDP 从配置构造并**默认放行**以不改变既有行为；行列级权限走 SQL 改写，见 #23 同批的计划条目）。

**教训**：接上还不够 —— 每个都要留一条"确实接上了"的用例（PII 那条断言"全链路四次 LLM 出站都不含原文"），否则下次重构又会悄悄掉。

### 26. 行列级权限初版的三个洞（安全特性必须用"绕过它的输入"去测）

初版自测全绿（20 例），但独立审查用真实代码当场打穿三处：

1. **列白名单只校验最外层投影**。`select order_id from (select phone as order_id from sales) t`
   —— 套一层子查询把禁列改个名，外层只看得到 `order_id`（在允许列里），**实测把 5 个手机号全部返回**。
   同理 CTE、以及 `WHERE / ORDER BY / GROUP BY / HAVING` 里的禁列都不校验 ——
   而"按禁列过滤/排序"本身就能反推出该列的信息。
2. **行过滤注入到了最外层 SELECT**，而不是"拥有受管表的那个 SELECT"。
   `select (select count(*) from sales) as n from other` 被改写成在外层补 `WHERE dept_id = 7`，
   受管表反而全量读出（返回 5，正解 2）；若最外层恰好没有同名列，就变成查询直接报错（假拒绝）。
3. **解析器的参数名写错且不报错**。sqlglot 30.x 里 `Select` 的 FROM 参数是 ``from_``（带下划线），
   写成 `args.get("from")` **静默取到 None** → 谁的表都定位不到 → 所有带行级规则的查询一律被拒。
   这类"取不到就是 None"的错不抛异常，只有用例能发现。
   （同轮还有一处：PG 的 dict 命名参数 `:name` 被 sqlglot 渲染成 `%(name)s`，而 SQLAlchemy 只认
   `:name` —— "PG + 命中规则 + dict 参数"这个组合直接失败，因为此前的参数用例只覆盖
   SQLite + `?`。）

**为什么自测没抓到**：我的用例全用"一条平铺的 SELECT"当输入，等于只测了最简单的那一种写法。
权限这类特性，**必须用"绕过它的写法"去测**（子查询、CTE、别名、自连接、跨层引用）——
否则绿灯毫无意义，甚至比没有权限层更危险：它给出的是**虚假保证**。

**修法与护栏**
- 列校验改为**整棵树**扫描指向受管表的列（子查询/CTE/过滤/排序/分组全覆盖），别名经 alias→table 映射解析；
- 行过滤注入到**唯一拥有该表的 SELECT**；归属不唯一（跨层多次引用、自连接）一律拒绝，不猜；
- 渲染后把 `%(name)s` 转回 `:name`；表引用计数保留重复（自连接时 `dept_id` 会歧义报错）；
- 新增 12 条回归用例覆盖上述路径；并修掉 4 条**假绿**断言 —— 它们用结果文本里的数字做包含判断
  （`"2" in text`），而文本里含"耗时 5**2**8 ms"这类数字，**结果全错也能通过**；已改为断言
  `artifacts.sql_result.rows` 的行集合。

**判据**：安全特性交付前先问一句"什么样的输入能绕过它"，把这些输入写成用例。

### 27. 角色由**调用方自称**：权限层可被请求体里的一个字段绕过

**现象**：服务端没有鉴权，而且 `role` 是**客户端在请求体里自己填的**
（`schemas.CreateTaskRequest.role` 默认 `"admin"`，`HarnessService.create_task` 的默认参数也是 `"admin"`）。
也就是说：能连上端口的人，默认就以 **admin** 身份跑任务，还能批准自己触发的高危操作。

**为什么危险得不显眼**：PDP（工具级）与行列级权限（数据级）这两层**都按 `role` 判定**，
而 `role` 从头到尾来自调用方 —— 权限做得再细，只要"我是谁"能自己填，就等于没有权限层。
这类缺陷在代码里看不出来（每一层单独看都是对的），只有把整条链路从"入口"串到"判定"才发现。

**解法**（2026-09-27）：新增服务端鉴权（`harness/server/auth.py`）——
角色**只能来自 `Authorization: Bearer` 对应的令牌**（`AUTH_TOKENS` 配置的映射），
请求体里的 `role` 字段**直接删除**（旧客户端传了会被 pydantic 忽略，不再有效）。
另外顺手补上：`/docs` 与 `/openapi.json` 一并鉴权、`?token=` 只对 SSE 路由生效
（浏览器 EventSource 不能设请求头，但查询参数一旦被普遍接受就是绕过鉴权的后门）、
审批需审批角色且**不能自批**（职责分离）、未配置令牌时**启动即失败**。

**判据**：凡"权限判定所依赖的身份"来自请求本身（body/query/header 里客户端可写的字段），
那层权限就不成立 —— 身份必须由服务端可验证的凭据推导。

## 二、文档与决策偏差

### 14. 计划的"降级条款"与实际实现/指示冲突

计划的风险表里明文规定了若干"外部依赖不可用时降级"的条款（消息队列、记忆、对象存储、沙箱各有降级路径）。但其中：
- **沙箱**那条已按指示**删除**（改为拒绝执行，不在宿主上回退），而**风险表没同步改**；
- **消息队列**那条已被明确要求**不得降级**。

**认知纠正**：这里混了**两种性质完全不同**的东西 ——
- **容错降级**：依赖挂了，系统装作没事继续跑（数据可能丢）
- **合法部署形态**：本就该二选一（如对象存储 / 本地文件），**根本不是降级**

**决定**：消息队列改为**"可靠投递"** —— 本地落盘缓冲、恢复后补发。**数据不丢、语义不变，只是投递延迟**。这与"降级"是两回事。

---

### 15. 人工审批机制**只有声明、没有闸门**（安全缺口）

**现象**：高风险工具被标记为"需人工审批"，但实际**会被直接执行**，全程没有审批环节。

**根因**：该标记全代码库只被读两处 —— 往给模型看的工具清单里加一句提示（**纯提示词**）、往审计里记一条"本次需要审批"（**只记录事实**）。执行流程里**没有审批闸门**。子任务级还有一个审批回调，但那是审"结果"的，与工具级是两回事。

**决定**：**不做临时版**。没有对外接口时审批人无处决策，临时闸门只能靠测试桩验证，会围绕一个将被替换的形态调优、**导致目标偏移**。改为采用**编排框架原生的中断能力**实现（同源、且与检查点天然配套），与**服务化同期**落地。

---

### 16. 配置层存在机器相关写死值与明文凭据

**现象**：配置里有**绝对路径**（换机器即崩）和**明文密钥**（已进版本库）。

**严重度如实**：密钥是本地开发用、服务仅监听本机，**实际风险低**，但**模式错误**；讽刺的是主配置文件被版本控制忽略，而密钥的**默认值**却写进了模板与配置类，等于绕过了自己的忽略规则。

**决定**：**不单独提前修**。辨析：**"删除写死值"与"换成什么注入机制"是两件事** —— 后者是部署决策（配置文件字面量 / 容器环境变量 / 密钥管理），而部署形态本身待定。现在就修必须先选定一个可能被替换的机制，**正是要避免的目标偏移**。随沙箱服务端纳入统一编排时一并解决。

**✅ 已收口（2026-09-28，A4）**：

### 17. 两份计划并行，必然漂移

### 23. 数据质量红线的阈值语义与真实数据冲突（计划 → 实现的偏差）

计划 §0.2 写"缺失率 > 30% 或波动异常则暂停分析"。按字面实现后，**示例链路第一步就被自己的红线拦住**：示例脏数据里的 `blank_note` 是整列全空（本来就是给 cleaner 删的），缺失率 100% > 30% → 暂停等人批。

**判定**：整列空是零信息量的**待删列**，不是"脏数据污染分析"；现实表格里整列空很常见，按 100% 拦会让真实数据永远进不了分析。**改规则**：只拦 (阈值, 100%) 之间的部分缺失，全空列交给 cleaner（体检器已把它单独标成 `all_null` 高风险，不会被静默忽略）。

## 三、基础设施运维

### 18. 沙箱服务端是"没人管"的进程

**现象**：沙箱服务端被当作一次性的后台进程启动，宿主内存紧张时被系统回收，**服务静默消失**；没有停止/查看/日志的手段，也没有防重复启动。

**已定位的根因**：它**尚未纳入项目的统一基础设施编排**，因此没有生命周期管理（内存上限、重启策略、日志归集）。

**决定**：按项目既定的基础设施编排方式纳管（**不另写脚本** —— 项目的编排机制只有一种），随编排收尾一并做。当前是过渡形态。

---

### 19. 活的连接管理器放进图状态，checkpoint 序列化直接崩

**现象**：C5 最初把 `DataSourceManager`（内含 SQLAlchemy Engine、连接池、线程锁）经子图 state 透传，任务创建后后台图立即失败：`Type is not msgpack serializable: DataSourceManager`，主流程一直轮询不到终态。

**根因**：LangGraph checkpointer（连内存版 MemorySaver 也一样）用 msgpack 序列化【整个 state】。Engine / 锁 / socket 这类活的运行时对象不可序列化，放进 state 必然在第一个检查点崩溃。

**解法**：`DataSourceManager` 与 Broker / LLM 同属【运行时基础设施】，经节点构造函数注入（`build_executor_graph → ReActNodes`），sql_query 经 broker invoke 的 context 取用，**绝不进 state**。

**判据**：凡含连接 / 锁 / 线程 / 文件句柄的对象，走构造注入；只有可序列化的纯数据（字符串、数字、dict、dataclass）才进 state。

---

### 20. 重复注册同名数据源，旧 Engine 被丢弃却不关闭（连接泄漏）

**现象**：pytest 全量运行时，`test_chart_generator`、`test_context` 名下冒出若干 `ResourceWarning: unclosed database in <sqlite3.Connection>`，且都在对象被 GC 回收时才抛出、归属到后面的测试；被归属的测试本身并不碰数据库。

**根因**：连接层 `register` / `register_sqlite` 在同名数据源重复注册时，用 `self._engines.pop(name)` 把旧 Engine 取出后**直接丢弃、没有 `engine.dispose()`**。旧 Engine 连接池里持有的 sqlite 连接就此失去引用却未关闭，直到 GC 才以 ResourceWarning 暴露。sql_query 对同一个 SQLite 文件每查一次都会重新 register 一次（`source_name` 同名），每多查一次就漏一个 Engine。**这是产品代码缺陷而非单纯测试卫生**：长期运行的服务反复查同一 SQLite 文件会持续泄漏连接。

**解法**：新增 `_dispose_engine_locked(name)`，`register` / `register_sqlite` 替换缓存前先 `dispose()` 旧 Engine；测试侧用 fixture（`yield manager`、结束 `close()`）并在用例后关闭、复位进程级 `_default_manager`。

**验证**：`pytest -W error::ResourceWarning` 严格模式下相关用例零警告；全量 55 passed / 1 skipped。

**判据**：凡"替换 / 弹出"缓存中持有句柄的对象，丢弃前必须显式释放 —— `pop` 只解除引用，并不释放底层资源。

---

### 25. Docker Desktop 端口代理让"连不上"变成 4 秒超时（测试挂死的真凶）

**现象**：一个"数据库连不上时工具要干净失败"的用例，把整次测试拖到 200 秒以上（表现为 pytest 卡住不动、无任何输出）。

**根因**：本机（Docker Desktop 端口代理 / 沙箱运行时）对**无人监听的端口**不是立刻 RST，而是把 SYN 挂住，**4 秒后才拒绝**；而 psycopg 默认没有连接超时，于是 `engine.connect()` 长时间阻塞，叠加连接池行为，一次测试能拖成几分钟。

**解法**：测试里所有真实连接一律显式带 `connect_timeout`；构造"一定连不上"的场景改用保留端口 + 瞬时拒绝的地址，别用"本机某个正常端口"。

**另一个迷惑点**：`docker pull` 的输出被管道接给 `tail`，缓冲区导致"一个字都看不到"，看起来像卡死 —— 长命令要么重定向到文件、要么别接 `tail`。同一轮里我因此误判了两次"镜像拉不动"，实际拉取是好的。

## 附：几条经验

1. **不报错的错最贵**。字段名不一致、配置没读到、失败被当成功 —— 全都是"看着正常"。真跑才能暴露。
2. **只在长任务发作的缺陷，短测试永远测不出**。上下文压缩切配对、审批缺失、路径口径不一致，都属于这类。
3. **"有模块"≠"生效"**。写完要接线、要透传、要验证默认路径真的走到。
4. **两份并行的文档必然漂移**。代码改了计划没改，就是下一次混乱的来源。
5. **别用"当前用不用得上"去裁剪架构**。企业级能力的取舍要看规划给它的定位，不看今天谁在调它。
