<a id="数据溯源校验方法"></a>
## 数据溯源校验方法

### 场景描述
报告中出现了“华东区上周GMV 1.24亿”，需要验证这个数字是否真实来自 VFS 中的分析结果文件，而不是 LLM 凭空生成的。

### 校验流程
1. **从报告中提取所有数字**：使用正则或专用解析器提取报告中出现的数值。
2. **匹配 VFS 文件**：在 VFS 中查找最近生成的相关分析文件（如 `attribution_20260921.json`）。
3. **比对数值**：将报告中的数值与 VFS 文件中的对应字段比对。
4. **标记结果**：匹配成功标记为“可溯源”，匹配失败标记为“不可溯源”。

### 提取与匹配示例
```python
import re
import json
from pathlib import Path

def extract_numbers(text):
    """从报告文本中提取关键数字"""
    # 匹配 "1.24亿"、"1,234万"、"85%" 等格式
    patterns = [
        r"(\d+\.?\d*)\s*亿",
        r"(\d+\.?\d*)\s*万",
        r"(\d+\.?\d*)%",
    ]
    numbers = []
    for pattern in patterns:
        numbers.extend(re.findall(pattern, text))
    return numbers

def load_vfs_numbers(file_path):
    """从 VFS 文件中提取数值"""
    with open(file_path, "r", encoding="utf-8") as f:
        data = json.load(f)
    return data.get("metrics", {})

def verify_traceability(report_text, vfs_file):
    """验证报告数字是否可溯源"""
    report_numbers = extract_numbers(report_text)
    vfs_numbers = load_vfs_numbers(vfs_file)
    
    results = []
    for num in report_numbers:
        found = any(str(num) in str(v) for v in vfs_numbers.values())
        results.append({
            "number": num,
            "traceable": found,
            "source": vfs_file if found else None,
        })
    return results

# 使用
report_text = Path("/reports/draft/weekly_report.md").read_text(encoding="utf-8")
vfs_file = "/workspace/reports/attribution_20260921.json"
results = verify_traceability(report_text, vfs_file)

for r in results:
    status = "✓" if r["traceable"] else "⚠"
    print(f"{status} {r['number']} → {r['source'] or '不可溯源'}")
```

### 输出示例
```text
数据溯源校验结果：
✓ 1.24亿 → /workspace/reports/attribution_20260921.json
✓ 85% → /workspace/reports/attribution_20260921.json
✓ 15% → /workspace/reports/attribution_20260921.json
⚠ 3.2万 → 不可溯源（报告中出现但 VFS 无对应文件）
```

### 校验失败的处理
- **数字完全不匹配**：以 VFS 文件为准，修改报告，标记为 Needs Revision。
- **数字在 VFS 中不存在**：标记为“不可溯源”，退回报告撰写环节补充数据来源，或删除该数字。
- **同一数字对应多个 VFS 文件**：需明确使用哪个文件为准，并在报告中注明。

### 自检清单
- [x] 已从报告中提取所有关键数字
- [x] 已在 VFS 中查找对应的分析结果文件
- [x] 已逐项比对，标记可溯源/不可溯源
- [x] 不可溯源数字已退回修改

### 注意事项
1. **数值格式需归一化**：`1.24亿` 和 `12400万` 应视为同一个数字，比对前需统一单位。
2. **百分比也要溯源**：如“提升 8.3%”应能追溯到原始数据。
3. **图表中的数据也要检查**：图片中的数字虽不能正则提取，但可通过生成图表的脚本和源数据检查。
4. **不可溯源是严重问题**：任何不可溯源的数字都可能意味着 LLM 幻觉，必须阻断发布。

<a id="结论支撑度评估量表"></a>
## 结论支撑度评估量表

### 评估量表

| 等级 | 判定标准 | 示例 | 处理方式 |
|---|---|---|---|
| **充分支撑** | 结论有明确的统计证据（p 值 < 0.05、95% 置信区间、贡献度分解、明确的因果推断方法） | “华东区下降贡献度 85%，p<0.01，数据见 attribution.sql” | 通过 |
| **部分支撑** | 结论方向正确但缺乏量化证据，或证据强度不足 | “华东区可能是主要驱动因素（贡献度未量化）” | 通过，但需在报告中标注“证据待补充” |
| **过度解读** | 结论超出数据范围（如用相关性推断因果、用单次观测推断趋势、忽略辛普森悖论） | “用户流失与页面改版有关”（无对照实验，无其他变量排除） | 退回修改 |
| **无支撑** | 结论与数据矛盾，或完全无数据来源 | “预计下季度增长 30%”（无预测模型和置信区间） | 阻断发布 |

### 过度解读的常见类型

#### 类型 1：把相关当因果
- **表述**：“A 事件导致 B 指标上升”
- **问题**：无 A/B 实验、断点回归、双重差分等因果推断支撑
- **正确表述**：“A 事件与 B 指标上升同期出现，建议进一步验证因果关系”

#### 类型 2：用单次观测推断趋势
- **表述**：“某指标连续 3 天上升，说明业务在恢复”
- **问题**：3 天数据不足以支撑趋势判断
- **正确表述**：“某指标近 3 天上升，需结合更长周期观察是否形成趋势”

#### 类型 3：忽略辛普森悖论
- **表述**：“整体转化率提升，运营策略有效”
- **问题**：未检查分组趋势，可能整体上升只是结构效应
- **正确表述**：“整体转化率提升，但各渠道转化率均下降，整体上升系流量结构变化所致”

#### 类型 4：外推超出数据范围
- **表述**：“基于 1 个月数据，预测全年 GMV 将达到 10 亿”
- **问题**：数据时间窗口过短，未考虑季节性、大促、政策变化
- **正确表述**：“基于 1 个月数据外推存在高度不确定性，建议延长观察周期或引入外部因素修正”

#### 类型 5：未量化的影响
- **表述**：“用户流失可能影响未来营收”
- **问题**：“可能”“影响”未量化，无法验证
- **正确表述**：“用户流失率上升 5%，按当前客单价估算，年化营收影响约 -XXX 万（置信区间 ±YY）”

### 评估流程图

```text
[结论] → 有数据来源吗？
          ├─ 无 → 无支撑 → 阻断
          └─ 有 → 有量化证据吗？
                    ├─ 无 → 部分支撑 → 通过并标注
                    └─ 有 → 证据支持结论方向吗？
                              ├─ 支持且强度足够 → 充分支撑 → 通过
                              └─ 支持但超出范围/方向相反 → 过度解读 → 退回修改
```

### 自检清单
- [x] 每条结论已按量表评估
- [x] 标记为“过度解读”的结论已退回修改
- [x] 标记为“无支撑”的结论已阻断发布
- [x] 标记为“部分支撑”的结论已在报告中标注

### 注意事项
1. **业务知识是必要补充**：某些结论在业务常识下合理，但缺乏统计证据（如“用户投诉与产品质量有关”），应由业务负责人判断，而非直接阻断。
2. **量表是辅助工具，不是绝对标准**：需结合报告用途（内部参考 vs 对外发布）调整严格程度。
3. **退改记录要保存**：每条被退回的结论都要记录原始表述和修改后的表述，便于复盘。

<a id="审查结论升级机制"></a>
## 审查结论升级机制

### 升级路径

```text
[初步审查]
    │
    ├── 全部通过 ────────────→ Accepted
    │
    ├── 可修复问题（一致性、部分支撑、风险提示缺失等）
    │       │
    │       └──→ Needs Revision ──→ 报告修改 ──→ 重新审查
    │                                              │
    │                                              └──→ 若再次不通过 3 次，升级为 Blocked
    │
    └── 不可修复问题（PII 残留、数据不可溯源、无支撑结论）
            │
            └──→ Blocked ──→ 人工介入
```

### Needs Revision vs Blocked 的判定

| 问题类型 | 判定 | 理由 |
|---|---|---|
| 摘要与正文数值不一致 | Needs Revision | 可修复，以 VFS 为准修改即可 |
| 部分结论缺乏量化证据 | Needs Revision | 可补充分析或改为相关性描述 |
| 风险提示缺失 | Needs Revision | 可补充 |
| PII 残留（未脱敏身份证号） | Blocked | 合规红线，不可发布 |
| 数字不可溯源 | Blocked | 可能是 LLM 幻觉，需人工核查 |
| 结论与数据方向矛盾 | Blocked | 逻辑错误，需重做分析 |
| 同一问题修改 3 次仍不通过 | Blocked | 疑似逻辑错误或数据问题，需人工介入 |

### 升级通知格式
```text
╔══════════════════════════════════════════════╗
║ 报告审查升级通知                              ║
╠══════════════════════════════════════════════╣
║ 报告名称：华东区周报                          ║
║ 触发升级：PII 残留                            ║
║ 问题详情：图表 3 数据标签中包含完整手机号      ║
║ 已尝试修复次数：0 次                          ║
║ 升级动作：阻断发布，通知数据合规负责人          ║
║ 处理期限：2 小时内响应                        ║
╚══════════════════════════════════════════════╝
```

### 人工介入流程
1. Agent 将 Blocked 报告推送至人工审批平台。
2. 审批人查看报告、审查日志、VFS 文件后做出决定：
   - **批准**：豁免具体问题（需说明理由），记录审计日志，报告可发布。
   - **退回**：退回报告撰写环节，附带具体修改要求。
   - **终止**：数据或分析存在根本问题，终止本次任务。
3. 所有决定记录到审计日志，保留不少于 3 年。

### 审计日志格式
```json
{
  "timestamp": "2026-09-30T16:20:00+08:00",
  "report_name": "华东区周报",
  "decision": "blocked",
  "trigger": "PII_residue",
  "details": "图表 3 数据标签中包含完整手机号 138****1234",
  "escalated_to": "compliance_officer_wang",
  "resolution": "pending",
  "sla": "2h"
}
```

### 自检清单
- [x] 可修复问题已判定为 Needs Revision
- [x] 不可修复问题已判定为 Blocked
- [x] 修改 3 次仍未通过的问题已升级为 Blocked
- [x] Blocked 报告已推送至人工审批平台
- [x] 所有决定已记录审计日志

### 注意事项
1. **Blocked 不等于终止**：只是暂停发布，人工介入后可能豁免或修改后发布。
2. **SLA 要明确**：不同严重程度的 Blocked 应有不同的响应时限。
3. **人工介入要有据可依**：审批人需看到报告、审查日志、VFS 文件才能做出准确判断。
4. **升级机制不是惩罚**：它是发现和修复问题的保障机制，不是对撰写者的追责工具。

## 与工具配合

本 Skill 的方法论与以下工具配合使用：
- `read_file`：读取 VFS 中的分析结果文件用于溯源校验。
- `sql_query.py`：核查不可溯源数字是否需要重新查询。
- `pii_compliance` Skill：PII 扫描发现残留时触发合规流程。
- `report_structure` Skill：本 Skill 审查不通过时，报告退回至该 Skill 重新生成。

**与工作流的关系**：
```text
report_structure（构建报告） → report_compliance_reviewer（独立审查）
    ↑                                │
    └──── Needs Revision ────────────┘
                                     │
                                     └── Blocked → 人工审批
```

如果审查结论为 Accepted，报告可发布；如果为 Needs Revision，退回修改；如果为 Blocked，阻断发布并升级至人工处理。
